第一部分（给人看）

1. 要做什么与运行一览

StopCube 里，方块在轨道上来回移动，单程步数 M 从 {60, 80, 120} 中随机取。模型要在方块第 N 次（N 取 2–5）经过目标中心时按按钮，正确时刻是 T(M,N)=M·N−M/2（scripts/interpret/hover_points.py::press_step）。StopCube 没有示范段，所以 motion token 全部来自执行过程中的画面。1105 的探针显示 MotionMem 的表征读得出速度 M，但那只是相关性。

本实验做的是因果干预：同一局、同一场景，只把 motion token 换成「方块单程步数为 M′」时的真实 token，画面帧不动，然后看按下步是否朝 T(M′,N) 移动。

供体 token 的造法：同一种子、同一场景，在环境里把方块的 move_interval 改成 M′。机械臂原样回放接收局自己的动作，到机械臂移到按钮上方就位为止，之后原地悬停、不按按钮。这样录下来的 motion token 和原局只差方块的运动，都是 motion 编码器在真实仿真画面上的输出，没有置零或删除。

每个接收局跑的条件做什么作用
N（原样）不干预，固定噪声种子 42得到原按下步 press_N
S（换噪声种子）不干预，噪声种子换成 1量模型自身的按下步抖动
D(M′)：录供体 ×3M′ 取三个值（含 M′=M），回放 N 的动作到就位，之后悬停，同时录 motion token得到三套供体 token
R_same（M′=M）换成同速供体，噪声种子同 N对照组：换录制版 token 本身不应改变按下步
R_fast / R_slow（M′≠M 的两个值）换成异速供体，噪声种子同 N主读数

规模：每个模型 72 个接收局 × 8 个回合 = 576 回合，两模型合计 1152 回合，不存注意力。资源为 GreatLakes 8 个单卡 A40 占位（每个占位一个长作业步、内含两条通道）加 aspen 2 卡。预计改代码加冒烟约 1.5–2 小时，正式运行约 3–4 小时，先跑 MotionMem 再跑 Wan。

3. 机制

3.1 按 token 时钟预测的偏移量 Δ*

方块位置 cube_position(t,M) 是周期 2M 的平滑往返，第 k 次经过中心在 t=M·k−M/2。如果模型完全按 motion token 里的速度数次数，就会在 T(M′,N) 按下：

M → M′N=2N=3N=4N=5
60→80+30+50+70+90
60→120+90+150+210+270
80→120+60+100+140+180
反方向（80→60、120→60、120→80）同表取负

例子：M=60、N=3 时正确按下步是 150。换成 M′=120 的 token 后，若完全按 token 时钟，模型会拖到 300 才按（Δ*=+150）；若完全不读 token 速度，就仍在 150 附近。

可作参照的先验：1105 rollout 里 MotionMem 在 M=120 时 15/16 按对，在 M=60、80 时多数按晚（17 局）。这说明它可能对速度有偏好，但没有因果证据。

3.2 供体怎么录

  • 改速度：third_party/robomme_benchmark/src/robomme/robomme_env/StopCube.py::_initialize_episode 设置 self.move_interval，step 用它计算方块位置。录供体时，由 stopcube_runner 在 reset 之后、第一步之前改写 env.unwrapped.move_interval=M′。这是运行时覆盖，不改 third_party 文件。正式干预回合不做这一改写，环境里的方块仍按真实 M 运动，官方成功判定照常。
  • 动作：逐步回放接收局 N 回合实际执行的动作，直到就位步 T_h，取「把机械臂移到按钮上方」这个子目标完成的那一步。从 T_h 起按现有 hold_extended 机制固定关节悬停，一直到官方步数上限，全程不按按钮。如果 N 回合没有到达就位，就取它按下前 16 步作 T_h；如果它从未按下，就取最后一步。
  • 录 token：服务端加 --record-motion，录下每个窗口（33 帧，起点 32u）的编码，按 sp-swap 的合成供体键写成 motion_swap_exact 供体文件。键号为 ep = 20000000 + recv×10 + slot，slot 取 0=M′60、1=M′80、2=M′120。每个模型用自己的编码器分别录制。

⚠ 陷阱与反例：

  • 如果干预回合比供体覆盖的时间更长，超出部分找不到同起点窗口，motion_swap_exact 不会替换。供体已经录到官方上限，理论上不会发生；仍用 SPEED_SCOPE 逐回合统计未替换的窗口数。
  • 在 M′=M 时，回放必须重现 N 回合的 token，否则 R_same 混进了回放误差。闸门是 REPLAY_EQ：比较 T_h 之前的窗口与 N 回合 --record-motion 的编码。
  • 回放之所以能用，是因为方块是运动学驱动的，不和机械臂发生碰撞。录制前用 MOVE_OVERRIDE 核对：环境里方块的实际位置要与 cube_position(t,M′) 吻合。

3.3 能说明什么、不能说明什么

  • β 显著大于 0，且 R_same 的 Δ≈0：MotionMem 的按下时机因果地依赖 motion token 里的方块运动。
  • β≈0：按下时机主要来自帧和文本，与交换任务上的结论同向。
  • Wan 作对照：按前几轮的经验，预期 β≈0。
  • 局限（K10）：M′ 同时改变速度和相位，区分不了「读速度」和「读位置相位」。还有一点，画面帧仍是真实速度，所以 β 的上限受帧信息竞争的影响。
