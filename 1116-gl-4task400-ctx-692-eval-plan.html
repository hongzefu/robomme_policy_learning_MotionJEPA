显存与内存都可能卡住。以往 GL 每片独占一卡，同卡多片在 A40 上没实测过；内存方面，作业 cgroup 现场已被训练留下的页缓存顶满（memory.current≈128 GiB，其中 file 91.5 GB、anon 43.8 GB），读总量做差没有意义。压测时只在 GPU0 起 N 片（N=每卡片数），判据四条，都满足才算 PASS：

  • GPU0 显存余量 ≥ 4 GiB（脚本原判据）；
  • 内存：读压测这一个 srun 步自己 cgroup 的 memory.stat 里 anon+shmem，压测期间最大值 − 压测前值 = 同卡 N 片总增量 host_delta_gb；host_delta_gb × 4 卡 ≤ 115 GB（R2）；
  • 超时：压测单局墙钟 wall_s 满足 20 × wall_s × 2 < 14400（每块 20 局共用 EVAL_TIMEOUT=14400，乘 2 留给 4 卡同跑的争用，R4）；
  • 压测的局本身 episode_ok、无 OOM 行。

CPU：16 核要分给 8 片的 server + client。env.sh 按 SLURM_CPUS_PER_TASK 设线程数，srun 步里是 16，所以链去掉这个变量，回到 AWS 的每进程 4 线程（K7）。

另外，local_692_pool.sh 的卡位满了会直接返回 97，不会排队。所以逻辑分片数必须等于卡数 × 每卡片数，即 8 或 4，一波起完。

五、触发与时间线

每条 run 一条 aspen 本机 tmux 链（g4c-ev512-chain / g4c-ev1024-chain），按顺序走四关，任何一关 FAIL 就停下，不往下走：

  1. 等训练：每 60 秒 grep ^EXIT_CODE= 训练日志。见 EXIT_CODE=0，且 50000/_CHECKPOINT_METADATA 存在、10 份 ckpt 齐全、tmux g4c-train-512 已退出、占位里没有训练 step（squeue -s）、评估环境就绪（V1–V3 已 PASS 的标记文件存在）才进下一关。见 EXIT_CODE= 非 0、tmux 已退却没有 EXIT_CODE=0、或出现 *.attempt*.log（训练改续跑），一律 CHAIN_STOP stage=train。CHAIN_WAIT 只在启动时打印一次，防 Monitor 限流。
  2. 加载冒烟：经 srun --jobid=<占位> --overlap --exact --ntasks=1 --cpus-per-task=16 --gpu_cmode=shared env -u SLURM_JOB_ID -u SLURM_CPUS_PER_TASK G6B_SHARE_FRACTION=0.38 … 跑 local_692_pool.sh --g6b <ckpt> 7。先在 GPU0 单片跑 1 局，再同卡 2 片各 1 局，期望 EVAL_LOAD_SMOKE=PASS。
  3. 压测：EVAL_PER_GPU=2 EVAL_MEM_FRACTION=0.38 --g6b-capacity。链脚本读 EVAL_CAPACITY 行，另出 HOST_MEM 与 CAP_TIMEOUT 两行（§三）。任一不过就用 1 / 0.70 再压一次，按 PASS 的那档定并发。
  4. 正式 692 局：EVAL_NGPU=4 EVAL_SHARDS=<8|4> EVAL_PER_GPU=<2|1> …，得到 EVAL692=PASS 和成功率。正式运行全程不读内存、不加采样（R-MEM）。

链本身只跑评估，不 scancel。收尾（写档案、scancel 本 run 的占位、更新状态机）由 Claude 会话在核到 EVAL692=PASS 之后完成。会话这边除了每份日志挂 Monitor，还沿用已改好的定时唤醒（每天 08:03、11-17 19:13、11-20 07:17）兜底，另加一次 11-20 16:07 的唤醒，免 ctx1024 评完后占位空等近一天。

五、风险登记

风险影响处置
128 GB 内存撑不住 8 片OOM killer 杀片V6 用压测期间 step 级 anon+shmem 增量 ×4 外推（HOST_MEM），超 115 GB 退到 4 片。压测每片只跑 1 局，外推是下界
A40 同卡 2 片显存不够冒烟或压测 OOMXLA 池外开销 6.3 GiB 是从 A100 推的；V5/V6 当场测，不过退每卡 1 片
单块 20 局超 14400 s该片不完整，整轮 FAIL、无重跑V6 的 CAP_TIMEOUT 外推，不过退档
卡位锁文件 flock 落在 turbo NFS 上锁失效时同卡超额V5 的 share2 和 V6 压测都经过同一把锁，能先暴露问题；若锁失效，链停下交你，不另加机制
aspen→GL 的 ssh 断开srun 随之被停，该关中断训练同样挂法已稳定数日，不改；中断即链停下、保留日志，按工程故障自行处理并在汇报里写明。链与 ctx1024 训练共用同一个 ControlMaster，主连接断开会同时停掉 ctx512 评估和 ctx1024 训练，训练侧按 1111 计划的续跑流程处理
节点上有别人的进程占用端口连错服务run_shard.sh 按 18011+7k 取端口；节点 GPU 归本作业独占，端口冲突概率低；出现 Errno 98 即停
装环境耗时或失败赶不上 ctx512 结束链等训练结束和环境就绪两个条件，晚开不影响结果；占位还有约 2 天余量
A40 推理慢于估计评估超过 10 小时占位余量足够；只记录，不处置

六、盲区诚实清单

  • A40 上每卡几片能跑、单片内存多大、692 局要多久，都没实测，全靠 V5/V6 当场定。
  • 新驱动 local_692_pool.sh 没有在 GL 已评过的 ckpt 上复现过历史数字，与对照组的差异见 §六。
  • context 1024 的推理显存比 512 大多少没测过，所以两条各压测一次，并发可能不同。
  • 新环境用 uv.lock 装，与 <GL_REPO> 那套 policy-eval 环境同一份锁，但没有逐包比对过；V3 只核 editable 指向。
