真正卡住的可能是内存。以往 GL 每片按 2 CPU / 32 GB 申请（gl_eval_shard.sbatch），这是申请量，不是实测值。所以压测时除了照 AWS 记显存峰值，还要记作业 cgroup 的内存峰值。判据有两条，都满足才算 PASS：

  • GPU0 显存余量 ≥ 4 GB；
  • 单片内存峰值 × 每卡片数 × 4 卡 ≤ 115 GB。

另外，local_692_pool.sh 的卡位满了会直接返回 97，不会排队。所以逻辑分片数必须等于卡数 × 每卡片数，即 12 或 8，一波起完。

五、触发与时间线

每条 run 一条 aspen 本机 tmux 链（g4c-ev512-chain / g4c-ev1024-chain），按顺序走四关，任何一关 FAIL 就停下，不往下走：

  1. 等训练：每 60 秒读一次训练日志末行，等出现 EXIT_CODE=0，并且 50000/_CHECKPOINT_METADATA 存在、10 份 ckpt 齐全。然后再确认 tmux g4c-train-512 已退出，占位里没有训练 step（squeue -s）。
  2. 加载冒烟：经 srun --jobid=<占位> --overlap --exact --ntasks=1 --cpus-per-task=16 --gpu_cmode=shared 跑 local_692_pool.sh --g6b <ckpt> 7。先在 GPU0 单片跑 1 局，再同卡 2 片各 1 局，期望 EVAL_LOAD_SMOKE=PASS。
  3. 压测：EVAL_PER_GPU=3 EVAL_MEM_FRACTION=0.30 --g6b-capacity。不过就用 2 / 0.45 再压一次，按 PASS 的那档定并发。
  4. 正式 692 局：EVAL_NGPU=4 EVAL_SHARDS=<12|8> …，得到 EVAL692=PASS 和成功率。

链本身只跑评估，不 scancel。收尾（写档案、scancel 本 run 的占位、更新状态机）由 Claude 会话核对判定行后完成。会话这边除了每份日志挂 Monitor，还沿用已改好的定时唤醒（每天 08:03、11-17 19:13、11-20 07:17）兜底。

  • export 行：MMEVLA_MOTION_OVERFLOW="${MMEVLA_MOTION_OVERFLOW-resample}"（空串表示关闭），EXPECT_MOTION_STATS="${EXPECT_MOTION_STATS:-1}"，POLICY_CONFIG="${POLICY_CONFIG:-mme_vla_suite_b128_80k}"；EVAL_ENV 回显行照常打印实际值。
  • ① E0 闸：DEMO_PREFIX_ORIGINAL=1 时打印 E0_GATE=SKIP reason=original_store store=$STORE，同时要求 $STORE/index.json 存在，然后继续；否则保持原逻辑。
  • --g6b-capacity：与 nvidia-smi 采样并列，起一个持久采样，每 2 秒读一次作业 cgroup 的 memory.peak（cgroup v2；不存在时用 memory.max_usage_in_bytes，两者都没有则写 host_peak_gb=unknown 并判 FAIL），结束即停；EVAL_CAPACITY 行加 host_peak_gb=。压测前先记基线，host_peak_gb 取压测期间峰值减基线。脚本只判原有的显存条件；§三 的内存外推由链脚本按 host_peak_gb/N*N_total 判，脚本不知道 4 卡外推。

在 RUNS 末尾按既有体例加两条，带中文注释，注明来源计划 1111 和本计划。resolved_sha256 取 run 根 history_config.resolved.sha256 文件内容（已读：512 为 9fa83497c0ce1e5b493b248c79e3c9b67efe03f9c7de2b84bf192a4932050d15，1024 为 70208fa373a470b5e0a19385d4a1db0984d3ed3bc70b8a635fe4f4cedf31e016）。合入后在主检出用 check_checkpoint.py --resolved-sha256 src/mme_vla_suite/models/config/robomme/perceptual-framesamp-context-{8,16}frame-8x8.yaml 复算，逐位一致才算通过。token_per_image==64 两条都满足（8×8）。
