第一部分（给人看）

1. 结论

同时跑两条 run，各占四卡，互为对照。两条都直接用未改动的官方条目 mme_vla_suite（src/mme_vla_suite/training/config.py:450），只在命令行指定数据路径、归一化目录和 history YAML，不新增 TrainConfig。相对原版，语义上只有一项改动：budget 从 512 改为 1024。

预计工期约 63 小时（2.6 天），合理区间 56–71 小时。这是外推值，正式起跑前用 300 步实测替换。两条并行，所以总墙钟时间也是这个数。

2. 「1024」按记忆预算理解

context 模式的 memory_token_dim 必须等于主干宽度 2048，FrameSampDataset 的形制断言也只接受 (context, 2048)，所以 1024 不可能是 token 维度，只能是 budget。每帧 token 数保持原版：framesample 16、tokendrop 64。framesample 因此从 32 帧变 64 帧，不改成 8×8 的 16 帧。motion 按原版关闭（motion.enabled 不开）。

4. 全量统计发现：tokendrop 大多填不满 1024

对 1600 个 episode、476857 个样本的全量统计（只读）：

指标tokendropframesample
样本填满 512 的比例26.9%95.3%（t≥32）
样本填满 1024 的比例8.2%90.5%（t≥64）
预算 512 时的平均有效 token317未统计
预算 1024 时的平均有效 token392976

原因是打分每 8 帧才做一次，且差异小于 1e-4 的 patch 直接跳过，平均每帧产生的 token 很少。把预算翻倍的增益集中在长历史任务：tokendrop 填满 1024 的比例在 VideoPlaceOrder 是 95.1%，VideoPlaceButton 是 74.9%，VideoRepick 是 4.4%，其余任务不超过 2.4%；StopCube、VideoUnmask 这类任务连 512 都基本填不满（0%、0.5%）。

后果有二：① tokendrop 在多数任务上和原版 512 取到的 token 几乎一样，不要预期全任务大幅提升；② 补零 token 仍占序列长度，两条 run 的算力开销相同，tokendrop 的效率会低一些。为了对齐原版，我建议不改打分参数，把这作为实验结果如实报告。

好消息：kept 堆只有 4/1600 个 episode 达到 2048（全在 VideoPlaceOrder）。训练用「整集最终堆再按 t 过滤」，在线用「截至 t 的堆」，两者只在堆发生过淘汰时才可能不同，所以这个原版固有差异在本数据上基本可以忽略。

5. 工期怎么估的

实测锚点：① context 512，四卡 b128 是 3.25 s/步，八卡 b128（每卡 16）是 1.727 s/步，比值 1.88（docs/training-doc/ctx-stock-scaling-20260928/result.md，GPU 利用率 99% 以上，是 GPU 瓶颈）；② context 2048，四卡 b128 是 10.09 s/步（mixed8-200-m32x8x8-context-b128-80k/result.md，显存 79445 MiB）。

前缀长度估为记忆加两路图像 512 再加文本 64：512 档 1088，2048 档 2624。由①②拟合 t ∝ L^1.29，1024 档（L=1600）相对 512 档慢 1.64 倍。四卡 b64 每卡 16，和八卡 b128 同密度，所以 1.727 × 1.64 ≈ 2.84 s/步，80000 步约 63 小时。显存预计明显低于 80 GB（每卡 16、预算只有上述 2048 档的一半；每卡 16 的 context 512 实测约 41.8 GB）。

6. 要改什么

  • 两份 YAML：从上游 perceptual-framesamp-context.yaml（去掉 motion 段）和 perceptual-tokendrop-context.yaml 复制，只改 budget: 1024。
  • 训练读取：FrameSampDataset 放开两个档位（(1024,16,1)、(1024,64,1)，都限定 context + 2048 + 无 motion）；新增 tokendrop 分支，逻辑照搬 mem_buffer.py::filter_token_dropping_indices。tokendrop 的训练入口在 V4.3 被删，但打分和取样函数还在，kept_indices.json 也已随库建好。
  • 在线记忆：当前 FrameSampMemory 不存像素、不打分，tokendrop 模型评估时用不了。需补一个最小的在线打分分支，否则模型训完无法 eval。本计划只实现并验证，不跑 eval。
  • 启动脚本：一份简单的双 tmux 启动脚本，不套 orig80k_contract 那类多层合同。

7. 不做什么

不开 motion，不跑 modulation，不改打分参数，不做学习率缩放，不改 mme_vla_suite 条目。本轮不评估成功率，eval 等训完另行确认；届时 tokendrop 与 framesample 都用官方 800 局比较。

8. 磁盘与风险

  • 磁盘：/scratch 剩 2.1 TB。8×8 库约 101 GB；checkpoint 按历史约 11.6 GB/份，8 份 × 2 条约 186 GB。够用。
  • HF 额度：两个 bucket 共约 186 GB。10-18 曾因 HF 额度满导致上传失败，开工前先查额度。
  • 单 seed：两条都只用 seed 42，与原版一致；差距小于约 2pp 时不足以判断优劣（既往三 seed 标准差约 0.6–0.7pp）。
  • 工期偏长：2.6 天里卡被全占，期间其他 GPU 任务要排队。

9. 子代理分工与合并（简述）

代码拆三块，各用独立 worktree 写：S1 训练读取和 YAML，S2 在线 tokendrop，S3 启动脚本。按 S1 → S2 → S3 合回工作分支，每次合并前后由 sonnet 审查（PRE/POST_MERGE_REVIEW）。8×8 打包和正式启动由主检出的运行代理负责，只启动、不改代码。主会话负责监听和上传登记。
