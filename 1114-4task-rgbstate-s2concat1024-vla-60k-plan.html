2. 为什么不重建库：三路 opus 对抗验证结论

16task 当时重建，是因为本机根本没有官方 16×100 的 VLA 库，而且 encoder 必须与 VLA 同源（1027 计划第二节原文：VLA 库清单「无」）。这是数据身份问题，不是格式问题。4task 的情况不同：旧库与 1113 encoder 用的是同一个 bucket revision、同一份 MANIFEST。这次派了三个只读 opus 代理，一个查血缘、一个查格式、一个专门找「必须重建」的反方理由，结论如下：

代理判定行关键证据
A 血缘LINEAGE_REUSE=PASSmember pin 2cb9026f… 用三条独立路径复算一致，各 1600 条：MANIFEST、policy 合并时本地实算的 record_dataset_<T>_episode_map.json::h5_sha256_local、encoder 的 control/source/<T>.receipt.json。合并时 merge_v2_h5.py 先逐个核源 sha，合并后用 compare_tree 逐 dataset 全值比对：MERGE_VERIFY=PASS level=full … episodes=1600 … mismatches=0。episode 顺序 1600/1600 一致。
B 格式FORMAT_REUSE=PARTIALSigLIP 源 pkl 605,611 个，norm_stats（sha 856c75ea）、episode manifest 字段与 16task 完全相同，可复用。缺三样：① 4×4 帧表：本机没有，bucket 里是同格式（framesamp-4x4-v1，schema 1，1,192,918 行，约 78.2 GB），可以拉回；源 features 674 GiB 当初没上传，不能在本机重打。② stage2 1×1024 motion 表：新产物，打包代码要能认 4task 来源。③ manifest 写死的 raw_dir 现在是空目录，要核实导出／打包是否必须用它。
C 反方REBUILD_REQUIRED=NOexec 端点：旧库的 exec_start_idx = encoder scope 的 D，num_timesteps = T，Σ(T−D) 正好 605,611。要补的 4 项都不用重建：血缘比对改代码、exec 段口径写进合同、latent 跨路径对拍、恢复 4×4。heldout 与 16task 先例一致，不排除（VLA 用全部 1600 集）。

⚠ 我先前「旧库没有逐成员 pin，所以要重建」的说法是错的：旧库缺的只是一条逐成员血缘记录，源本身就是同一份。补记录用 S1 新增的 member_pin 比对模式，判定行同 P-LINEAGE 格式，不放宽、不 WAIVE。
