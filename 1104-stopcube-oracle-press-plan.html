第一部分（给人看）

要做什么

让 Oracle 把机械臂送到按钮上方并保持。模型照常接收真实画面，每过 4 步被问一次「要不要往下按」，每次给 10 个预测，只记录不执行。每个询问点的完整输入和输出都存盘，之后不用再跑环境，就能离线继续问模型。最后再挑一部分预测真正执行，验证「想按」的判断是否可靠。

用户原话：

  • 「通过 simulator 本身直接计算出它这个真正的下压位置区间，然后……用 Oracle 的 Planning 的 model 直接去到达这个位置，然后再来……进行模型的推理……然后去判断这个模型真正按下去的这个可能的比例有多少。」
  • 「你写一个新版的方案，不要修订原来的方案了」
  • 「问这个模型的采样间隔还是再密一点……你可以降低到四步。你先降低一些比例，先用十个预测，然后你再验证一下，就是真按下去是不是能够按到。」
  • 「不是每四步推理一次，是每过四步问一次要不要往下按。这是我们的 Oracle 可以每过四步多问一次。」
  • 「第一遍就不要再记录了……把这个所有的完整的输入什么的都记录下来，输入输出都记录下来，这样我们可以之后就可以直接的离线的问就可以。」

为什么要问整段悬停期

按 50 局的真实 seed 推算（M、N 取自 StopCube._initialize_episode 的同一随机序列）：

只问区间前后也分不出「判断对了」和「总想按」，所以要和其他时刻比较，尤其是前几次方块经过目标的时刻。

机制

询问为什么不影响模型。代码里每帧的记忆在 add_buffer 时写入，帧采样和 motion 窗口只由当前帧号决定，询问只读不写，所以多问几次不改变记忆内容。模型默认每次必须收 16 帧，这是评估客户端和 runtime_contract.py 两处的校验，模型本身没有这个限制；本计划只在 scripts/interpret/ 的询问模式里按 4 帧发送。这一点还没实跑，由 INPUT_CADENCE 判定行验证。

为什么存输入就够离线。采样函数 f_sample_attn 的全部输入是模型权重、observation 和噪声。这些都保存后，换任何分析工具重算都得到同一批动作，不需要再跑环境。OFFLINE_REPLAY 判定行验证这一点。

想按的判定。对每个预测的 20 行动作逐行换算目标 TCP 高度。z_hover 取本局 Oracle 悬停段的实测高度，因为定义值 0.15 m 与第 16 局模型实际悬停高度约 0.160 m 差了 1 cm，相对 2 cm 阈值不能忽略。

想按(s, t)        = s 的前 16 行里存在 z < z_hover - 0.02
起始行 r(s, t)    = 其中首个满足的行
P(t)              = 10 个预测中想按的比例
预计触发(s, t)    = t + r + d          # d 为命令到触发的实测耗时
落在区间内        = 预计触发 ∈ [target_visit_in, target_visit_out]

真按验证。走到询问点 t 后分两种：执行选中预测的 16 行，或不注入预测直接交还模型；此后每 16 步由模型真实推理并执行，直到按下或该局结束。这样测的是从这个时刻起真能否按到，而不是单个动作块。

怎么读结果。主图横轴是「询问点距 T 的步数」，纵轴是 P(t)，按 M 分面，并按方块第几次经过分组。

现象含义
只在第 N 次经过之前升高能区分次数和时机
每次经过都升高能感知方块位置，但没数对次数
第 N 次也不升高，或全程平坦这段历史下基本不想按，或与方块经过无关
上升时刻系统性偏早或偏晚时序偏差，配合真按验证的触发步核实

4.3 验证选点 verify_plan.json

放手点 = 最大的 t ∈ {1+4k}，满足 reach_step ≤ t ≤ T-48
         无解时取最小的 t ≥ reach_step，须 t < target_visit_in，记 late_release；仍无解记 none
第 N 次经过段 = [T-48, target_visit_out]
A = 该段内 P 最高的询问点（同值取较早）里序号最小的想按预测
B = A 同一询问点里序号最小的不想按预测
C = 前 N-1 次经过段内 P 最高点里序号最小的想按预测
P 为 0 或无候选的类别跳过并记原因。顺序：放手 → A → B → C

规则只读询问结果和固定阈值 2 cm，生成后固定，不按验证结果调整。注入动作从 query_<seq>.npz 读取。验证从询问点起，模型每 16 步真实推理并执行，使用原采样路径，不存注意力。第 16 局放手点为 369。

五 分析定义

  • 高度：TcpReader.set_arm 逐行换算，(10,20)；只表示目标姿态的高度，不是实测 TCP。
  • 耗时 d：对验证运行和正常局，用同一 z_hover - 0.02 取已执行命令首次过阈值的步到按钮触发的步，按 M 报告分布，取中位数。Oracle 耗时单独报告，不混入。没有足够下压局时，预计触发相关结果写「不可得」。
  • 经过分组：按 visits 把询问点划到第 1…N 次经过及其之间。报告 P(t) 均值和局级 bootstrap 区间。
  • 想按判定对照表：A、B、C 三类分别报告「注入后 32 步内按钮是否触发」和最终结果；同时给 1、2、3 cm 下各预测的判定变化。换阈值由用户决定。
  • 放手结果：按真实触发步分「早于区间／区间内／晚于区间／没按」，任务成功字段独立报告。
  • 对照：放手结果与正常结果只比较分布，两者历史和随机数不同，不解读单局差异。

十 盲区诚实清单

  • P(t) 表示「预测动作满足下压判据」，不等于按钮触发或任务成功。每点 10 个预测，单点比例分辨率只有 0.1，需靠多局和相邻点汇总。
  • Oracle 历史是理想条件。如果真实失败来自模型自身轨迹的累积偏差，询问结果看不出来。
  • 真按验证每局只有少数几个点，选点依赖规则；late_release 的局不能与其他局直接合并。
  • 只有一个模型 seed、50 局，部分 (M,N) 格子只有 2 局，结论不能外推。
  • 目标高度来自关节目标的运动学换算，真实 TCP 有滞后。
  • 离线重算只能回答同一输入下的问题；要改变历史就必须重跑环境。
  • 本计划不回答「模型依据什么决定下压」，只保证第二阶段有可用的输入数据。
