二、motion、官方协议与成绩

R01 P1 确认包丢失后重发，会改变历史或随机数

反例：16 帧已被 server 加入历史，但 ACK 丢失；客户端把原批次重发。现有 policy.py::add_buffer 根据 len(images) 自行分配新帧号，同一批像素会成为后续 16 帧。infer 每次调用还会 split RNG，响应丢失后重发也会改变采样噪声。

证据：policy.py 的 add_buffer／infer；历史请求没有 episode／batch 序号。下方 CPU 实验验证了这个控制逻辑缺口，但没有运行实际编码器。

最小修法：增加 episode nonce、batch_seq、first_global_frame、payload SHA 与 replanning_seq 做校验／审计。首版不做跨断线 ACK 缓存；不确定提交就废弃该局 attempt，禁止在原 memory／RNG 上重发。确认旧 client、server 内 RPC 和 sidecar 请求全部结束；不能确认时重启 server＋sidecar，然后同环境 seed／model seed 整局重跑。重试额度按原 episode 累计，最多额外一次。

验收：丢 ACK、重复批次、同序号不同 payload、丢 infer 响应、编码中途异常；不得把重复帧变成新帧，不得在半更新缓存上继续。改变 N 或领取顺序不能改变一局的 PRNG 调用序列。

R02 P1 两个合法客户端可以互相 reset 同一个 policy

反例：旧 sim 尚未退出，新 sim 已连上相同 server；两者都具有正确 run identity，交错调用 reset／add_buffer。现有 websocket handler 共用 self._policy，仅核 server nonce 挡不住合法连接之间的状态污染。

最小修法：每个 server 同时只允许一个活动 attempt 会话；第二连接在 reset 前拒绝。worker 确认上一个 sim 及其子树退出后才创建下一个，slot 在 GPU 初始化前还须取得独占启动许可。端口以真实 bind 结果为准。

验收：两个 client 交错 reset、同 slot 重复启动 worker、旧 client 延迟退出；只能一个会话修改历史和 RNG，不能以最终结果唯一掩盖推理过程已受污染。

R03 P1 视频故障不能使已经失败的任务获得重跑机会

反例：环境正常返回 fail，随后视频编码或 NFS 写入失败；若必须视频闭合后才记录终局，controller 会把整局当 infra error 重跑。重试可能 success，形成与产物故障相关的选择性重跑偏差。同 seed 并不证明整个模拟器／planner 逐位确定。

最小修法：terminal outcome 与 artifact receipt 分开。环境终态一确定，先持久化小型不可变结果；视频、日志关闭与 SHA 是后续产物验收。已有 terminal 的局只能修复已有采集材料，不能重跑 policy 改结果。终态未能持久化而发生崩溃时，明确标为 uncertain_terminal，不能宣称不存在重复执行风险。

验收：在终态后、视频中、close 中、receipt 发布前注入错误；原 success／fail／timeout 不变。执行覆盖和产物覆盖分别报告；缺失产物不能通过删除该局或重跑挑结果解决。

R04 P1 D 与 q 必须是官方返回观测的序号

反例：从底层视频帧或物理 step 重建 fixture，却忽略 wrapper 的 NO RECORD 过滤、reset 内初始动作以及 terminal 时的内部附加 step。窗口 oracle 仍可算得完全自洽，但使用的不是官方 client 实际收到的历史。

证据：官方 DemonstrationWrapper.reset 与 _step_batch、EnvRunner.get_init_obs/step。front 图像与状态的读取时刻也应进入来源 trace。

最小修法：fixture 记录过滤前后映射、reset 附加观测、终止处理与 front／state 配对，保留官方行为，不修改 benchmark。合法首包必须原子包含 D 个 demo＋exec0；“不同拆包等价”只针对首包后的 exec 续包，partial-demo 首包应明确拒绝。

验收：D=0／16／17／48／49／50、首包缺尾、q=31／32／63／64、内部多步／过滤 trace；逐帧核来源，而非只核长度。

R05 P1 PASS 日志不能代替可迁移的参考数组

事实：check_stage2_online.py 的 references.npy 在临时目录中生成，退出即删除；训练根快照也不会自动封入全部 G4／G6／G7／G12 材料。只有误差或 SHA，不能恢复原张量。

最小修法：列出 reference bundle：原始 RGB、33 个帧号与像素摘要、latent、认证 packed 行和索引、训练 pos／视觉／state、EMA 来源与固定噪声等。若保留了原 G0 映射与已认证 packed 表，可用 CPU 按映射抽取 packed-reference；源码已有同 latent 输出与 packed 行逐位一致的依据。它不等于找回旧 A100 在线 RGB 输出，不能扩大 G2 例外。

验收：移走原机器路径后离线使用；缺数组、错行号、变更一个像素、替换表、空集合、NaN、自填全零误差均拒绝。约 64 个原图窗为 396 MiB、64 份 latent 为 36 MiB，只是材料量级估算，不代表这些文件当前已存在。

未决边界：没有现成可交付原材料时保持 pending，不能为完成本计划擅自在 AWS GPU 上重算，也不能拿 A40 自己生成的参考冒充训练参考。

R06 P1 motion 数值通过不等于整个 VLA 在 A40 数值通过

反例：motion encoder 输出在阈值内，但 JAX 的 SigLIP、在线重算的位置码、state 归一化或 bf16 参数恢复不同。只检查动作 shape=(20,8) 和 finite 仍会漏掉实际差异。现有位置表工具已记录 CPU 与旧表约 7e−7 的差异，不能用“同一函数”代替实物对拍。

最小修法：增加具名 vla_stack_numeric 门：使用一份确实存在、与正式推理配置相容的 A100 参考 checkpoint，锁配置、normstats、完整 obs／noise、num_steps=10 和目标环境，对 pos／视觉／state／memory／全20×8动作及执行16×8动作分别报告。动作误差须明确归一化与物理单位，阈值在运行前冻结，不能验证后调宽。

60k 证据边界：现有自动动作参考主要来自20步短测的step19，不应假定60000自动有A100动作真值。60000必须做严格恢复、明确bf16转换后的逐叶核验与固定输入重复性；缺少同checkpoint跨卡真值时写 cross_gpu_same_checkpoint=NOT_AVAILABLE。推荐结论限定为“目标栈参考数值通过＋60k严格恢复／重复性”，不能推导60k跨卡动作误差上界。若要求更强结论，则真值缺失是额外硬阻断。

未决边界：真实参考或预先动作阈值不齐，vla_stack_numeric=PENDING；门表必须消费此状态，不能出现正文待定而启动器全PASS的旁路。

R07 P2 mask 需要验证实际被 attention 消费

反例：容量 padding 输入全零且 mask 正确，但线性层 bias 将零行投影成非零；若后端未使用对应 mask，仍会影响动作。只对装配 tensor 做比较不足以证明最终屏蔽。

最小修法与验收：对被 masked 的槽位施加有限大值扰动，memory attention／动作不应改变；D=0、q=0或16时全部motion为空也应无NaN。用可控、已知敏感的 attention 参数做解除屏蔽正控。不能强制真实 checkpoint 翻转任意 motion mask 后动作必须变化，因为模型可能合法地对该输入不敏感。

三、交付、环境和数值来源

R08 P1 三个进程需要三个受控环境

事实：policy 主环境为torch2.7.1／numpy<2；stage2为torch2.9.0／numpy2.4.4；官方sim另有torch2.9.1等要求。一个 EVAL_PY 无法代表全部运行栈。

反例：NFS venv解释器指向aspen本地/data；editable或.pth导入旧树；HF_HUB_CACHE覆盖HF_HOME；离线VAE缺revision引用。登录节点测试能过，GL才报错或加载不同资产。

最小修法：逐进程列解释器realpath、sys.prefix、锁摘要、实际包__file__、启动命令、显式缓存根及VAE／tokenizer／benchmark资产清单。使用NFS可见解释器，在计算节点禁默认HOME缓存和PYTHONPATH注入做离线预检；不用AWS venv复制品。

验收：错解释器、旧editable包、外部缓存覆盖、缺离线引用应失败。实际安装和资产齐备仍是现场待验，不以文档矩阵替代。

R09 P1 旧恢复脚本硬编码两张GPU和特定step

反例：在单A40分配中使用原 check_stage2_checkpoint.py：它要求父GPU0和sidecar GPU1，delivery仅60000、smoke仅19，早期5000也不能直接验证。

最小修法：新eval专用 check_runtime.py 接收实际分配GPU token／UUID、明确验证step与目标证书，复用参数树／shape／dtype／finite／文件闭合的验证逻辑。旧训练G12入口保持原语义，不把旧G12或上传.done改名为新单A40通过。

验收：CPU mock覆盖单GPU、早期step、60000、错误step和缺叶／多叶／错shape；随后在获准A40席位实测恢复与启动。

R10 P1 60k不能等待final总清单，也不能从可变目录加载

事实：增量发布器提供 manifests/step-60000.json；delivery_manifest.json 的final生成可能要等全部16份checkpoint齐全。

反例：等final清单导致60k即测变成等80k；或者先校验60000目录，下载器随后覆盖同名文件，模型实际加载了另一份内容。

最小修法：消费封口root清单＋step-60000清单的可信发布身份。下载到新staging，核成员集合、大小、SHA和路径闭合，拒绝外逃及未声明符号链接；发布到manifest摘要命名的不可变实体目录并原子写READY。worker不跟随latest或可被覆盖的同名别名。

验收：缺最后分片、root错配、清单中途改变、同名替换、未封口下载和发布后改文件均失败。60000的稳定可用性与训练任务running／done分开判定。

R11 P2 文档提交不能移动已经验证的执行源码

反例：commit C签发证书，再在同一NFS执行checkout提交报告变成D；严格核HEAD会无谓失效，忽略HEAD又可能漏掉真正源码改变。开发时rsync进运行树还会让后续client读取新代码。

最小修法：开发树→审定代码C→独立NFS执行release C→测量报告→证书→最终run identity。报告放run产物，文档提交不移动执行release。修复创建新release并按影响矩阵重验；motion报告不能反向引用尚未生成的证书摘要。

验收：开发树变化不改变执行release；执行树实际import／锁／源码变化被拒。证据依赖图必须可以拓扑排序，不含自摘要或未来依赖。

R12 P2 固定基线中的默认配置仍可能有占位符

事实：基线Stage2 YAML的checkpoint摘要仍曾为 __FILL_AFTER_G3__，后续上游提交才填入真实值。正式恢复读取交付resolved snapshot可避免它，但fixture或默认入口未必如此。

最小修法：生产一律核验交付快照，不用源码默认YAML覆盖；入口拒绝占位符。确需上游修复时记录具体commit／hunk、理由、身份变化和重跑门，不整分支漂移。

验收：默认文件与交付快照冲突时明确选已核快照或失败；移植后只声明实际重验的门通过。

R13 P2 ETA公式正确，仍可能没有跨机可读的进度来源

反例：aspen watcher配置AWS绝对日志路径，永远读不到；只用很久前的5000步发布，又无法识别训练暂停或速度改变。

最小修法：只读使用已有、具名的W&B run或既有交付事件，记录training_run_id／step／事件时间／接收时间与新鲜度，不静默改训练流程或SSH训练机。ETA_ready包含训练剩余、保存、发布、传输和校验估时；无可信来源则UNKNOWN或用户显式给到位时间。实际ready仍以文件封口硬门为准。

验收：错run、步数回退、训练重启、乱序、陈旧及未来时间戳不得触发盲提交；可信事件恢复后只幂等触发一次。

四、弹性N池与故障恢复

R14 P1 只把N移出身份，还不能防止重复申请整池

反例：C0已申请N个hold；A40验证发现问题，修代码C1或改CPU规格。如果schedule摘要包含这些字段，新watcher得到新schedule和空账本，再申请N个，旧资源仍活着。

最小修法：稳定pool／schedule intent与代码、模型、证据、资源revision分离。修订必须接管旧membership和全部UNKNOWN；改变评估语义需要新evaluation identity并排空旧负载，但可复用原pool持有的资源。禁止靠新目录隐藏旧job。

验收：RUNNING／PENDING／UNKNOWN均存在时修改代码或规格，旧job仍全部在账，不自动重新申请整池。

R15 P1 恢复冻结必须包含迟到的submit／launch

交错：controller冻结members={w1,w2}；此前发出的srun回执还未登记，w3随后启动。controller确认w1／w2死亡便提升generation，w3却仍拿旧许可计算。

最小修法：submit、launch、resize和reclaim由同一控制者串行登记。RECOVERING纳入SUBMITTING／UNKNOWN／STARTING／DRAINING／CANCEL_REQUESTED实例，冻结新入池；迟到回执只能补记存在，不能绕过恢复。死亡证明绑定membership revision、不可复用slot_instance、JobID incarnation与StepID。

验收：暂停srun回执后启动恢复，再释放回执；迟到worker在加载模型／领取前被拒，旧membership证明不得沿用。

R16 P1 先提升generation，可能把应该保留的正常结果判成过期

反例：五局块前两局已封口、第三局崩溃；先generation++再检查旧sealed结果，会丢掉前两局。若第一次infra error已写无覆盖canonical，重试success又无法替换；按新chunk计retry还会重新领取额度。

最小修法：冻结→确认旧执行停止→先接受旧代已持久正常terminal→持久化原episode剩余集合和累计额度→提升generation并发ready。首次infra error只进attempt历史，不能先占正常accepted；整个恢复事务可重放。

验收：每个写点崩溃后恢复，前两局不重跑，余项最多额外一次，拆块或worker重启不重置额度。

R17 P2 controller自身也有ownerless窗口

反例：创建NFS控制锁目录后、写owner前崩溃；两个接替者同时确认旧PID死亡，第二个可能误删第一个刚建立的新锁。网络失联也不等于旧主已经停止写入。

最小方案：首版选择aspen或vail的一台明确 controller_host，使用宿主进程生命周期锁，NFS只记审计与状态。不做自动跨机主备；迁移宿主先停止旧主并确认退出，不确定则停写。

验收：空锁崩溃、双接替、旧主失联恢复；永远只允许一个控制者。自动高可用不属于本轮弹性job数量要求。

R18 P1 UNKNOWN提交和重复srun都需要实例身份

反例：sbatch成功但回执丢失，accounting暂时查不到，于是重复提交；或者同一hold被两个launcher同时srun，chunk claim各自成功却在同GPU加载两套模型。

最小修法：提交前持久化pool／slot_instance／submission_id，写入可查询标签并使用可解析回执；核cluster、user、account、标签、提交时间及执行实例。零结果或查询失败仍为UNKNOWN，不能等固定秒数就认定未提交。启动还需要独立launch_id和slot独占；requeue／restart视为新执行实例重新核验。

领取回执也要幂等：controller已持久化assignment却丢失回复时，worker不能重试后再领下一块。每个slot_instance最多一个未终态assignment；claim_request_id重试返回同一个attempt，不确定先查询原grant。

验收：丢提交／领取回执、延迟记录、同标签多条、旧JobID、重排队和双srun；不得补交、额外授权第二块或接管错误资源。Slurm记录可能有重复JobID，见sacct官方文档；实际字段能力仍需现场确认。

R19 P1 缩容不能凭进度文件猜测“这局还没开始”

交错：worker缓存ACTIVE，controller已标retiring；worker随后抢块。另一种情况是sim已开始第四局，但controller看到旧进度，以为第四、五局未开始并重发。

最小修法：retiring单调，领取后启动前复核当前实例许可。worker明确handback已终局、当前局和未开始成员；controller在sim／step退出后才重新发布余项。正常缩容未开始项不扣infra retry。N=0只是drain，不是评估完成。

验收：把缩容卡在claim前后、下一局启动前后；归还集合与已执行集合不得重叠。N大于剩余任务数不能制造额外任务或重复计算。

R20 P1 desiredN不能成为无限续48小时的理由

反例：target N不变，一个hold自然TIMEOUT；对账器发现容量少一份又申请48h。并发从未超N，累计GPU小时却无限增长。第47小时扩容也可能把整轮延长到95小时。

最小修法：自然到期、显式扩容和续批是不同事件。默认到期只drain留队列，不由desiredN自动补交；启动前记录允许的并发、单job规格、累计GPU小时及campaign截止边界。每hold按自身StartTime／EndTime计时；检测requeue或实例改变重新验证，不假定站点默认策略。

验收：未获续批授权时，自然TIMEOUT不得因desiredN对账自动补交；只增加revision不是续批授权。迟起PENDING和晚期扩容不越过本轮预算。资源包络在未来启动时由用户明确，计划不替用户填固定数量。参见sbatch官方文档。

R21 P2 同一宿主的N个进程不足以验证跨节点NFS

反例：aspen同机并发测试通过，GL计算节点却读到旧目录／属性缓存；或者canonical直接指向仍会被worker覆盖的结果文件。

最小修法：至少两个独立NFS客户端，其中包括正式计算节点挂载；测试重开、暂停读取、EEXIST、旧目录视图和断开恢复。controller生成自身不可变descriptor，再无覆盖发布；不把可变worker文件硬链接为权威对象。产物内容仍由SHA回读核验。

验收：发布后worker改原结果，canonical不变且artifact SHA不符被发现。不能用sleep若干秒或“目录看起来空”作安全判据；不能承诺防住同UID恶意篡改。缓存语义见NFS文档。

R22 P2 五局能放下模型，不等于任意N能在48小时完成

上限核算：按每局2400秒、每五局另1800秒，800局合计 800×2400+160×1800=613.33 worker小时。这是建议超时上界推导，不是实测平均耗时，不应用来直接决定N。

最小修法：根据profile、剩余任务与各hold实际EndTime报告完成区间和剩余worker小时；不要求全部N同时RUNNING，已就绪者可先计算。限制同时冷启动数，防NFS加载风暴；跨至少两次sim生命周期观察常驻server／sidecar的FD、RSS、显存。记录输出量、配额和receipt保留空间，ENOSPC停止领取，不重复启动计算。

验收：晚到席位、N下降、加载拥塞、视频短写和跨块泄漏；要么有界完成，要么明确留下未完成任务，不能临时缩短官方步数来赶时间。

R23 P1 持久step与短命sim的死亡边界不能混用

反例：sim崩溃，resident worker却仍活着等下一块；controller坚持等整个step终态才重发，双方互等。drain若只在局间检查，卡死sim永远到不了检查点。

最小方案：正常chunk只回收sim，模型常驻；infra故障时首版worker封口已有结果并退出整个resident step，controller确认后再恢复。清理有独立本地deadline，按已登记进程／step实例逐级TERM、KILL；无法确认退出不重发。取消step不等于释放hold，最终job另核。

验收：sim忽略TERM、sidecar关闭卡住、NFS失联、PID重用；只能进入已终止或明确未确认，不能误杀其他scope，也不能假报资源释放。参见scancel官方文档。

R24 P1 首个A40通过不能替全部新增节点背书

反例：扩容加入另一driver或不同实际import路径的节点；它只复制首节点的PASS证书，模型实际软件栈已不同。或者证书仅验report SHA和status，report自填全零误差也能通过。

最小修法：每个新slot实例核GPU UUID／家族、driver、实际包路径、锁、资产和模型身份；不在证书适用环境内则重新验证或拒绝入池。验证器从锁定reference与实际测量数组独立重算指标和样本集合，不能只信自报PASS。

验收：错driver、错import、漏样本、NaN、空报告、自填max_abs=0或修改报告后重算自身hash均拒绝。这里防的是错误配置和不完整证据，不引入额外签名基础设施。
