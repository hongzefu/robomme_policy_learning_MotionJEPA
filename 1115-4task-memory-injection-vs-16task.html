4task 两条 VLA 的 memory 注入机制，与 16task concat 版逐跳对照

2026-11-15 美东。说明文档，不是计划。代码口径：policy 仓分支 sub-mem-inject，基线 01fe4ec；路径省略前缀 src/mme_vla_suite/。所有形状来自读代码与 yaml，没有跑训练、没有加载模型；参数量按权重形状手算。

用户问题：「Context concat 和 Modulation concat 这两个……他们这个 memory 注入的这个机制是什么，和之前我们训的这个十六 task 是不是完全一样？就是它这个注入的每一每一步的这个尺寸是不是都完全一样的？」

结论

注入机制完全一样，用的是同一份代码。从「进入投影层」开始往后，每一跳的张量形状、每一层可训练参数的形状和数量，4task 与 16task 完全相同。不同的地方只在投影层之前、帧记忆那一路的「怎么切」：4task 是 8 帧、每帧 8×8＝64 个 token；16task 是 32 帧、每帧 4×4＝16 个 token。两边乘出来都是 512 个帧 token，所以后面的形状对得上。

motion 那一路（每窗 1 个 1024 维 token、96 个窗位、stride 32）两边逐键相同。4 份 yaml 两两 diff，同一种注入方式下只差 token_per_image 一行（64 对 16）。

所以答案是：尺寸一样，内容不一样。同样是 512 个帧 token，4task 的每个 token 看的画面更细（2×2 个 SigLIP patch 的均值，16task 是 4×4 个），但时间上采的帧更少（8 帧对 32 帧）。

1. 两种注入机制

1.1 modulation：memory 不进主序列，action 一侧每层单独读一次

608 个 memory token 投影到 1024 维后，不经过任何 Transformer 层，直接交给 action expert。action expert 的 18 层里，每层多一个交叉注意力 MemoryAttention：action token 做 query，memory 做 key／value。读出的向量不加到残差流上，而是经 MemoryRMSNorm 变成一组 scale／shift，去调制这一层 FFN 的输入。paligemma（看当前图像和语言的那一侧）完全看不到 memory。

环节做了什么代码锚点
送入mem_seq=[None, mem_seq]：只有 action expert 一侧收到 memorymodels/integration/history_pi0.py::HistoryPi0.compute_loss、sample_actions
读取Q 来自 action token [B,20,1024]，K／V 来自 memory [B,608,1024]；4 个 Q 头、1 个 KV 头、head_dim 256（写死）models/integration/history_gemma.py::MemoryAttention.__call__
屏蔽只屏蔽补位的 key（mask 为 False 的位置 logit 置 −2.38e38）；没有因果限制同上
调制Dense(1024→2048) 把读出向量拆成 scale、shift，作用在 FFN 之前；原来的 pre_ffw_norm 保留history_gemma.py::MemoryRMSNorm.__call__、HistoryBlock.__call__
18 层每层各有一套参数，18 层读的是同一份 memoryhistory_gemma.py::Module.setup（nn.scan，mem_seq 走 nn.broadcast）

RoPE 位置号：MemoryAttention 自己编号，key 是 0..607，query 是 608..627（mem_len 取含补位的总长）。主序列（当前图像、语言、action）的位置号不受 memory 影响。4task 与 16task 的 mem_len 都是 608，所以这里完全相同。1030 计划 §3 写的「896 对 608」是 split 与 concat 两种读法之差，不是 4task 与 16task 之差。

1.2 context：memory 拼在主序列最前面

608 个 memory token 投影到 paligemma 的宽度 2048，放在「当前图像、语言」之前组成 prefix，和它们一起过 paligemma 的 18 层。action token 在每层原有的联合注意力里读到同层的 memory。没有新增的注意力模块。

环节做了什么代码锚点
拼接prefix ＝ memory 608 ＋ 当前图像 2×256 ＋ 语言 64 ＝ 1184 个位置，后接 action 20 个history_pi0.py::HistoryPi0.embed_prefix；两路相机见 policies/robomme_policy.py；语言长度为 HistoryPi0Config.max_token_len 默认 64
谁能看谁memory 只看 memory；当前图像不看 memory；语言和 action 能看 memoryhistory_pi0.py::make_attn_mask（ar_mask、na_mask）
推理含 memory 的 prefix 各层 K／V 在去噪循环外算一次并缓存history_pi0.py::HistoryPi0.sample_actions

RoPE 位置号：整条序列按有效位累加，positions = cumsum(input_mask) - 1（compute_loss）。memory 排在最前，所以后面的图像、语言、action 的位置号都被往后推，推多少等于 memory 里有效 token 的个数（补位不占号）。公式两边相同；实际数值取决于每个样本有多少有效帧 token 和 motion 窗，见第 3 节。

3. 逐项回答「是不是每一步尺寸都完全一样」

完全相同的

  • 投影层往后的全部张量形状（上表第 7–14 跳）。
  • motion 路从离线表到投影的每一跳（第 9–11 跳）。同一种注入方式的 4task 模板 yaml 与 16task yaml，motion 节逐键相同。
  • 总槽数 608、memory_token_dim（modulation 1024、context 2048）。
  • 可训练参数的形状与数量，见下表。没有任何一层的形状依赖帧数或每帧网格：投影层只看最后一维（2048、768、1024、256），注意力层的权重与序列长度无关。
  • modulation 的 RoPE 编号：key 0..607，query 从 608 起。

这些差异不改参数形状，但会改变「同一个位置号上放的是什么」。两处值得知道：

  • modulation：补位排在最尾，query 固定从 608 起，所以 query 到最后一个有效 key 的距离＝608−有效 token 数＋1。有效 token 数相同时两边一致；差别只来自每个样本的有效帧 token 数与窗数。
  • context：action 的位置号＝有效 memory 数＋当前图像与语言的有效数。同理，随每个样本的有效帧 token 与窗数变化。

4. 与 4task 既有无 motion 基线的关系

4task 这次的帧记忆配置与既有的无 motion 基线相同，只多了 motion 的 96 个槽：

yaml 对比差异
perceptual-framesamp-modul-8frame-8x8.yaml（modulation 512）对本次 modulation 模板除首行注释外，只多出整个 motion 节；budget 512、token_per_image 64、memory_token_dim 1024 等帧路键逐行相同
perceptual-framesamp-context-8frame-8x8.yaml（context 512）对本次 context 模板帧路键与 memory_token_dim 2048 逐行相同；基线的 motion 节是 enabled: false，本次是 enabled: true 的 stage2 concat 版

落到模型上：memory 长度从 512 变成 608；多两层投影 motion_pos_proj、motion_encoder_static（modulation 多 2,033,408 个参数，context 多 3,869,440 个）；帧路投影和 modulation 的 18 层注入模块形状不变。motion 关闭时这两层根本不创建，也不做重排（percep_mem.py::PerceptualMemory.__init__、history_pi0.py::HistoryPi0.embed_memory）。
