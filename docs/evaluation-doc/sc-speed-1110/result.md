# StopCube motion 速度替换：结果

**一句话结论**：把 MotionMem 的 motion token 换成「另一种方块速度 M′」的真实 token 后，它按按钮的时刻几乎完全跟着 token 的速度走。按下时刻的偏移对预测偏移的斜率 β=0.91，95% 区间 [0.84, 0.97]。按新速度算成功的有 76/144，原样回合碰巧落在同样窗口里的只有 2/144。按真实速度的成功则从同速对照组的 36/72 掉到 3/144。Frozen Wan 完全不跟（β=0.055，区间 [−0.00, 0.13]），按真实速度的成功基本不变（77/144）。

起跑信息见 [launch.md](launch.md)，散点图见 `records/delta_vs_pred.png`（两模型并排，已目视检查）。

## ① 读法

- **偏移量**：Δ = 替换回合按下步 − 原样回合按下步（只算两边都按下的局）；Δ* = T(M′,N) − T(M,N) = (M′−M)(N−½)，即「完全按 token 时钟数次数」时应有的偏移。β 是 Δ 对 Δ* 的带截距回归斜率，按接收局重采样 2000 次给出区间。
- **快 / 慢 / 同速组**：M′<M 为快组（token 比真实快，预期提前按），M′>M 为慢组，M′=M 为同速对照组。
- **成功判断**（用户追加的「新速度下能不能 success」，计划 §3.3）：
  - 官方成功等价于按下步落在第 N 次经过的几何窗口 W(M,N) 内；
  - 新速度成功 = 按下步落在 W(M′,N) 内。W(M′,N) 由同场景、方块单程 M′、悬停不按的供体录制轨迹实测得到，不靠公式；公式只作交叉检查，偏差为 0。
  - 基线 = 原样回合的按下步碰巧落在 W(M′,N) 内的比例。

## ② 主结果

| 判定行 | MotionMem | Frozen Wan |
|---|---|---|
| `SPEED_FOLLOW`（全量） | β=0.913 [0.837, 0.967]，n=133 | β=0.055 [−0.001, 0.132]，n=126 |
| `SPEED_FOLLOW_SYM`（替换回合也只算 M·N 之前的按下） | β=0.684 [0.517, 0.858]，n=86 | β=0.024 [−0.004, 0.074] |
| `SPEED_FOLLOW_ADJ`（以同速对照组为参照） | β=0.806 [0.640, 0.924] | β=0.022 [−0.003, 0.069] |
| 新速度成功，快组 | **32/72**（基线 2/72，差 +0.42 [0.31, 0.51]） | 13/72（基线 14/72） |
| 新速度成功，慢组 | **44/72**（基线 0/72，差 +0.61 [0.49, 0.73]） | 5/72（基线 0/72） |
| 按真实速度成功：快 / 慢 / 同速组 | 0/72 / 3/72 / 36/72 | 40/72 / 35/72 / 36/72 |
| 原样回合官方成功 | 38/72 | 40/72 |

对称截断口径的 β 小于全量口径，是预料之中的：慢组本该在 M·N 之后才按，截断后这部分大多被剔除。

MotionMem 按 (M→M′) 分格的平均 Δ 与 Δ* 同号，量级也接近：

| 格 | Δ*（N=2…5） | 平均 Δ [95%] |
|---|---|---|
| 60→80 | +30…+90 | +49.2 [24.7, 70.1] |
| 60→120 | +90…+270 | +148.8 [93.9, 195.3] |
| 80→120 | +60…+180 | +106.8 [78.9, 134.4] |
| 80→60 | −30…−90 | −56.7 [−71.0, −41.3] |
| 120→80 | −60…−180 | −107.8 [−131.1, −82.5] |
| 120→60 | −90…−270 | −161.8 [−196.1, −126.0] |

Wan 各异速格的平均 Δ 在 −8 到 +15 之间，区间都包含或贴近 0。

**一个强信号**：MotionMem 慢组有 54/72 回合在真实环境的 M·N 之后才按，其中 30 个按在真实方块 5 段运动结束、已经静止之后（`SPEED_LATE … after_cube_stop=30`）。画面里方块已经不动了，模型仍按 token 里的运动节奏「数完」才按。

**`PRESS_LABEL` 为 FAIL 的原因**：两模型共 20 个不一致回合，全部按在几何窗口入口那一侧，距起点 0 或 1 步，几何窗口判为窗内而官方判失败。这是几何窗口入口与官方判定之间 1–2 步的边界偏差，判据本身没有改。

为了看这个偏差会不会影响结论，另做了一个敏感性分析（`records/edge_sens.txt`，脚本 `records/edge_sens.py`）：把窗口起点往后收 2 步重算。MotionMem 的新速度成功从 32/72 变成 24/72（快组），从 44/72 变成 43/72（慢组）；基线仍是 2/72 和 0/72。结论不变。

## ④ 计划外事件与实施中调整

1. **开工审查自裁（计划〇′）**：用户说「不用再来找我了直接开始吧」。B1–B5 都是补全接口细节：
   - 供体关超时并跑到 H=max(M,M′)·N+32；
   - StopCube 放开 plfull；
   - 定死 speed_donor 配置字段；
   - N 阶段录 motion；
   - 冒烟改为 3 局。
2. **动作表口径**：真实首步的 env_step_before=1、env_step_after=2，所以回放表改按步前值对齐，并通知了 SC-W2。
3. **干预回合关超时（`commitV4.5.4`，`ADJUST_REVIEW=PASS scale=same`）**：
   - 问题：冒烟发现慢组 3/3 未按。原因是真实环境在 M·N 之后未按就判败结束，而 T(M′,N) ≥ M·N（只有 (60,80,N=2) 两者相等），慢组在结构上无法观测。
   - 处理：干预回合也只改 stop_time=99 并跑到 horizon；move_interval 与官方成功窗口都不变。
   - 冒烟中的旧口径干预已归档到 `smoke/runs-failed/iv-timeout-on/`，并用新代码在 GL 重跑。
   - 原样和换种子回合没有改，所以读数加了对称截断口径。
4. **aspen 名下的 n 队列改到 GL 跑**：
   - 机械地改写了解释器、checkpoint、运行树、contract 的路径；原件保存在 `motion/specs-aspen-orig/`。
   - 第一、二次漏改 `cuda: "1"`（GL 单卡），报 `No visible GPU devices`，归档在 `motion/runs-failed/a2g-B-{1,2}/`；改成 `cuda: "0"` 后第三次跑通。
5. **GL 排队**：8 个占位只排到 4 个。排不到的占位名下的队列，由空出来的已运行占位依次接着跑；剩余 4 个在 MotionMem 跑完后取消。
6. **release 补打**：iv spec 生成时 HEAD 是状态机提交 `17bfb50`。它与 `3802c24` 只差 `current.json`，为它补打了一个 release。
7. **手工启动的 tmux 转义**：会话日志末尾的 `EXIT_CODE=` 值为空，成败以 `SCS_HOLD … rc=0` 为准。

## ⑤ 限制

- **速度与相位混在一起（K10）**：换成 M′ 时，同一时刻方块的位置也变了，所以区分不了模型读的是速度还是位置相位。
- **帧仍显示真实速度**：MotionMem 的 β 已接近 1，说明在 StopCube 上 motion token 压过了画面帧；Wan 的 β≈0 也可能部分来自它更依赖帧。
- **对称截断口径**：只有全量口径能读出慢组；对称口径的 β 偏小是结构原因。
- **样本量**：每格 6 局，单格均值很宽，主结论依赖整体的 β 和新速度成功率。

## ⑥ 结论与下一步

在 StopCube 上，MotionMem 的按下时机因果地取决于 motion token 里的方块运动。换一种速度，它就照那个速度数次数，几乎是一比一地平移，甚至在真实方块停下之后仍按 token 节奏按下。Frozen Wan 不读 token 的内容。这与前几轮交换任务和多步任务的结果形成对照：那几个任务里 token 内容几乎不起作用，而 StopCube 这种计时类任务是 motion token 真正被读取的场景。

没有自动解锁的下游。可选的后续：做纯速度版本（对帧做时间重采样后再编码），把速度和相位分开。
