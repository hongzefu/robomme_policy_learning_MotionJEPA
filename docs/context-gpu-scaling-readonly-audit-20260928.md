## 2. 不满足“读取链路也不改”的三项实质问题

### R1：索引取证实际增加了数据交付工作

`context_gpu_scaling.py::IndexedDataset.__getitem__` 复制样本字典并加入 `_diagnostic_sample_index`。`run` 将这个包装对象交给 `TorchDataLoader`，新增字段经历堆叠、共享内存传输以及 `jax.make_array_from_process_local_data`，直到 `next_batch` 才移除。每个计时内 `advance` 都调用 `next_batch`，设备索引引用还持续保留到结尾。

索引没有进入最终模型观测，也没有发现原数组值或sampler随机流被改变，但“模型输入值不变”不等于“dataloader和读取链路原样”。只有最终索引回读和摘要在计时外；索引组装、搬运、分片和引用维护仍在被测路径中，影响大小未经动态测量。

### R2：大预算改用配对读取配置，不能当原context入口

`context_gpu_scaling.py::run` 在 `budget > 512` 时，把 `reader_history` 改成 `integration_type=modulation、memory_token_dim=1024`，模型保持 `context、2048`。生产 `train.py::main` 则将同一份解析后的history同时交给模型和读取器。

`FrameSampDataset.__init__::new_shape` 目前只允许大预算modulation，因此这个配置分叉实际避开了context守卫。数据字节曾经对拍相同，也不能把它称为原context生产读取入口原样可用。本轮不修改守卫、不换读取器。8192在新工具中明确为 `BLOCKED_INPUT`，尚没有性能结果。

### R3：观测组装禁用了原本存在的类型检查

`context_gpu_scaling.py::next_batch` 在 `at.disable_typechecking()` 中调用 `HistAugObservation.from_dict`；正式 `DataLoaderImpl.__iter__` 没有这层禁用。这改变了数据交付时的检查行为及主机工作量，不能归入“原读取链路不改”。

**处置仅记录：三个问题均未修复，该草稿不按当前约束放行。**

## 3. 计时与并发结论的主要缺口

| 编号 | 具体证据与影响 | 静态结论 |
|---|---|---|
| T1 | `run` 每10步额外同步 `(state,batch)`，窗口结束后写JSON/输出不计时，worker却继续预取 | 统一计时协议仍不同于生产持续异步循环；窗口和的吞吐不等于连续墙钟吞吐 |
| T2 | 默认预热10步，测第10–69步；原 `log_interval=100` 的周期聚合在计时内执行0次 | 不能声称已覆盖生产周期日志成本；W&B、保存及最终等待也未包含 |
| T3 | 常驻worker预取为 `2×workers`，屏障与窗口间停顿可补满16/32个batch；只测60步 | 短窗可能暂由队列储备掩盖持续读取不足，未有稳态饥饿或队列平衡证据 |
| P1 | `active_train_start` 在预热和屏障等待前记录；`check_parallel` 用这一大区间证明持续负载 | 等待也被算作活跃，某侧迟到时可能误报完整并发；实际起跑偏差仅输出、不约束 |
| P2 | 比较器只用首末窗口检查整体墙钟范围，未约束中间窗；`keepalive_steps=0`也可声明更晚的活跃终点 | 静态构造的矛盾区间可通过，不能只凭时间包络证明全部窗口有真实同伴负载 |
| P3 | `baseline_group` 未检查前后基线目录、UUID和时间独立性 | 同一份八卡记录可被重复当成两次，报告 `replicates=2` 和零漂移 |
| P4 | mixed模式只做各variant的八卡/四卡配对，未交叉核对两组公共源码与环境 | 各组分别自洽但条件不同的记录，可能被合成一份混合工期外推 |
| P5 | `barrier` 按原字符串去重participants；JSON读取和稍后的文件SHA不是同一字节快照 | 路径别名可把同目录当两参与者；起跑内容与记录摘要可能不一致；后续比较器能拦住部分情形 |
| P6 | 窗口耗时使用monotonic正确，但墙钟覆盖没有与单调钟增量对照 | 调时或调度停顿可损害跨进程区间证明；未确认当前机器实际发生此问题 |

正常尾部保持负载确实调用同一个 `advance`，延续模型状态和真实数据迭代；问题是现有证据不能完整证明每个对端测量窗口都处于共同持续负载中。不是断言所有正常运行必然不重叠。

## 4. 生命周期、输入契约与验收强度

### 4.1 生命周期

- `run` 的保持负载循环只等 `measure_done.json`，不读同伴 `failure.json`、不核同伴存活；对端OOM或退出时，本侧会持续训练直到外层1800秒超时。直接调用Python入口没有这项外层时限。
- wrapper外层没有完整的 `TERM/INT/HUP` 转发与等待清理。仅终止入口shell PID时，训练子进程可能继续运行。这是静态风险，未执行终止实验；本轮没有杀任何已有任务。
- 首次/末次NVML查询及采样器停止后的 `wait` 没有期限。1800秒只包训练命令，不是整个入口的完整上限。
- 最后一个 `tee` 写盘失败时，终端可能先看到 `EXIT_CODE=0`，随后脚本才以1退出；仅监听成功字符串不足。正常训练失败、超时和第一段管道失败的非零传播已有保护。

### 4.2 明确的参数与输出问题

- `arguments` 默认512、无motion、workers16，而所选60k基线要求workers8；默认正式调用会被一致性守卫拒绝，不会静默误跑。
- CLI可表达大预算motion组合，但对应YAML不存在，生产守卫也不支持；不应通过补文件规避当前限制。
- shell只识别完整 `--out-dir/--devices`，下游默认argparse允许缩写。缩写可使shell验证与Python实际参数分离；Python父目录限制仍在，不等于任意越界写入。
- 运行标签和公共缓存目录共用名字空间，`jax-cache` 等标签可能与后续缓存路径冲突。shell写文件早于Python规范路径检查；当前实际祖先目录为实体目录，未发现本轮已有越界写入。

### 4.3 比较器的独立验收缺口

这些是静态反例或复现性边界，不代表正常生产者已经生成伪造记录：

- 顶层 `schema`、`worktree_status`、跨运行HEAD未完整验证；部分必需源码、计时器和包版本字段可共同缺失而仍相等。
- 模型、预算、motion宽度、基线60k/80k等主要检查“双方相同”，没有全部绑定到权威固定值；外层预算未和内部history预算逐项相等校验。
- 数据摘要有的仅检查键存在；相同空身份或同样偏离权威归一化内容的记录，不能靠双方一致排除。实际 `resolved_data` 确有归一化数组完整摘要，不能说完全没有数据内容证据。
- 测量索引完整比对了60批、7680个值及其摘要，这是有效检查；但独立比较器未检查重复/上界。正常生产者本身的全程去重又可能在合法跨epoch场景误报。
- 前两批内容只检查每叶首尾各32元素，不能证明全批字节一致；报告已写出这一范围。比较器仍缺少对“恰两批、非空完整叶集、摘要字段类型”的结构验证。
- 部分合法但错误类型的JSON会触发未捕获异常，缺少 `REJECTED` 报告；比较报告直接写目标文件，可能留下半份报告。
- 比较器未独立核对所有 `failure.json`、分层退出码、末步标量、完整有限性和更新证据；正常采集器的有限性/非零退出保护仍有效，不能将这些反例说成已发生假通过。

### 4.4 环境与资源证据

- 新工具只做资产锁cheap检查，未独立重做完整权重SHA；此前完整资产检查不能自动被新结果当成自身证据。没有发现当前权重已改变。
- 实际来源覆盖变量、部分allocator/线程变量、CUDA运行库/驱动指纹没有完全固定和留档。三草稿未完整约束未验证数据库逃生开关，不能无条件宣称其输入一定verified。
- 物理GPU只以数字声明和型号比较，没有完整UUID映射。比较器确实拒绝重复的数字四卡集合，但不能靠同型号证明同一物理设备。
- NVML统计覆盖整轮初始化、编译、预热、测量和收尾，不是稳态利用率；同时间戳和过大采样间隔缺少完整性拒绝。主机采样也未独立证明覆盖全部测量窗口。
- RSS相加可能重复计共享页；shm和MemAvailable是主机全局值，不能把双任务记录相加归因。
- 没有完整排除其他任务、页缓存预热、温度/功率/频率变化；固定seed反复读取相同样本可能让后测受益于页缓存。不能仅据短窗把差异全部归因于GPU数量。

## 5. 已确认正确的部分

- 正式性能模式每个任务global batch128，单进程local batch同为128；四卡/八卡每卡分别32/16。双四卡是两个独立128任务，不是一次128更新被拆成两个任务。
- `jax.device_count == args.devices` 与原 `make_mesh` 的组合能防止可见8卡却冒充4卡；JIT输入/输出分片、donation和 `sharding.set_mesh` 作用域与原调用相同。
- 直接调用原 `init_train_state/train_step`，保留完整主干、bf16、冻结过滤器、AdamW、裁剪、EMA、全部训练参数梯度和 `state.step` 递增。没有发现启用mask候选、attention替身、physical-loss AST或局部梯度训练。
- `train_rng/init_rng`拆分与 `fold_in(rng,state.step)` 链相同；索引记录不消费训练随机流。当前seed42一致，硬编码42只是未来配置漂移风险。
- 数据变换复用生产 `transform_dataset`，原数组值与sampler顺序没有发现主动篡改；这不抵消第2节的数据交付变更。
- 六个等长窗口的均值、样本/秒、单组慢倍数和双任务理论公式正确。六个相关窗口并未被报告成独立实验或置信区间。
- 正常容量模式、缺少六窗口、非零退出、缺完整结果等会被比较器拒绝；不能笼统说比较器没有失败保护。

## 6. 尚不能回答的速度数字

本次只读检查不产生新的训练性能实测。先前原 `train.py` 入口的单卡、batch1、worker1两步与原生保存成功，能证明那条真实读取/训练链路可执行；不能推导八卡与双四卡的稳态速度。

旧容量数据也不是此次对照：原mask若干档位只有编译超时；四卡512/2048通过和4096/8192的OOM涉及候选mask，后者另有关闭自动调优的实验；记录只有两步、重复同一真实样本、workers0且不保存。不能把这些数字拼成“原机制双四卡比八卡慢多少”。

待真正获得符合约束的观测值后，应分别报告：

```text
每个模型的慢倍数：t4 / t8
双四卡合计吞吐：128/t4a + 128/t4b
同配置两份等步数任务的并行/八卡串行时长比：max(t4a,t4b)/(2*t8)
512(60k)+2048(80k)的条件外推比：
  max(60000*t4_512,80000*t4_2048) / (60000*t8_512+80000*t8_2048)
```

这些公式不是测量值。完整工期还涉及初始化、编译、周期日志、checkpoint、长期数据轮次与快侧结束后的资源变化。当前不提供未经实测的倍数。
