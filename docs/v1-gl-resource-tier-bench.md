# v1 集群作业 CPU / mem 档位实测

> 状态：**方法与判据已定，实测数据待回填**（`step_bench.sh local` → `cluster` → `report` 之后）。
> 目标：在**不掉 GPU 利用率**的前提下，把 8 个 1-GPU job 的 CPU 与内存申请压到尽可能低，
> 减少排队与配额争用。数据链路的整体方案见
> [`v1-gl-dataset-consistency-report.md`](v1-gl-dataset-consistency-report.md)。

---

## 一、为什么值得压（实测理由，不是习惯）

### 1.1 配额是组内共享的，CPU 最紧

chaijy2 账户配额（2026-08-23 实测）：

```
上限:  GPU 20  |  MEM 960 G  |  CPU 80
当时:  GPU  1  |  MEM  38 G  |  CPU  9
```

8 个 job 的三维占用随档位变化：

| 档位 | GPU | CPU（占配额） | MEM（占配额） |
|---|---:|---:|---:|
| 4 CPU / 16 G | 8 / 20 | 32 / 80 = **40%** | 128 / 960 = 13% |
| 2 CPU / 12 G | 8 / 20 | 16 / 80 = **20%** | 96 / 960 = 10% |
| 2 CPU / 8 G | 8 / 20 | 16 / 80 = 20% | 64 / 960 = 7% |
| 1 CPU / 8 G | 8 / 20 | 8 / 80 = **10%** | 64 / 960 = 7% |

**CPU 是三维里最紧的一维**（80 的总量对 8 个 job 而言很浅），压它的边际收益最大。

### 1.2 节点碎片：有空闲卡却零空闲 CPU

spgpu 当时 240 张 A40、空闲 76 张、23 个节点有空闲卡。但其中四个节点是这样的：

| 节点 | 空闲 GPU | 空闲 CPU | 空闲 MEM |
|---|---:|---:|---:|
| gl1501 | 3 | **0** | 234 G |
| gl1500 | 2 | **0** | 36 G |
| gl1508 | 2 | **0** | 86 G |
| gl1514 | 1 | **0** | **4 G** |

**GPU 空着但 CPU（或内存）被占满**，是「明明有卡却一直 PENDING」的常见真相。
降低 CPU 与 mem 申请能扩大可调度节点集合。

### 1.3 档位 → 可立即起跑槽位数（实测，这是压低收益的直接度量）

把「压低档位有多少好处」量化成一个可直接对比的数：**当前 spgpu 上，各档位下能立即起跑的
1-GPU job 槽位数**（逐节点取 `min(空闲GPU, 空闲CPU÷档位CPU, 空闲MEM÷档位MEM)` 再求和）。
2026-08-23 19:20 实测，spgpu 空闲 A40 共 **77 张**：

| 档位 | 可立即起跑的 1GPU 槽位 | 相对 4CPU/16G |
|---|---:|---:|
| 4 CPU / 16 G | 39 | — |
| 2 CPU / 12 G | **52** | **+33%** |
| 2 CPU / 8 G | 52 | +33% |
| 1 CPU / 8 G | 55 | +41% |

（我们只需要 8 个槽位，所以此刻**任何档位都能立刻全起**——这是当下的宽松状态，不是常态。
真正的意义在于：档位每降一档，能容纳我们的节点集合就大一圈，组内其他人占满资源时的
抗挤压能力就强一分。CPU 维的边际收益最大，因为 spgpu 节点是 8 卡配 32 核，
每卡「公平份额」只有 4 核，要 4 核就等于卡在公平线上。）

### 1.4 两个否定性结论（省得后面走弯路）

1. **`sbatch --test-only` 的起跑时间估计不可信。** 实测它对上述四个档位一律报
   「2026-08-27 起跑」，即约 4 天后——而同一时刻 spgpu 有 77 张空闲 A40、
   我们这档有 39–55 个可用槽位。原因是它把假想 job 排在**全部 PENDING job 之后**，
   而那 77 个 PENDING 里绝大多数卡在 `AssocGrpBillingMinutes`（各自账户的计费限额）、
   **根本不与我们争抢物理卡**。判排队要看逐节点空闲量，不要看 `--test-only`。
2. **chaijy2 没有计费分钟瓶颈。** `GrpTRESMins = billing=345,987,911,907`（约 3460 亿分钟），
   实质无上限；`AssocGrpBillingMinutes` 是别的组的问题。我们的真实约束只有
   GPU 20 / MEM 960 G / **CPU 80** 三项。

## 二、压过头的风险（先验判断，待实测证伪）

`MemoryBuffer.add_buffer` 是**逐 timestep 调用、每次只喂 1 张图**的，SigLIP 单次前向极短；
而 CPU 侧每步要做 h5 解压、`einops` 像素重排、`np.abs(...).mean` 像素差、`np.save` 588 KiB、
`pickle.dump` ~400 KiB。**所以流水线大概率本就偏 CPU/IO-bound，降 CPU 的风险明显大于降 mem。**

内存侧的先验：峰值大概率出现在**启动时载入 1.66 GB 的 `siglip_params.pkl` 并转 jnp**
（瞬时 host 峰约 3–4 G）；稳态是 `MemoryBuffer._history_feats` 按**整个 episode** 累积
（最长 586 步 × ≈784 KiB ≈ 0.44 G）。

## 二·五、A40 单机探针实测（2026-08-23，先于扫档做，用来定位内存下限）

先用两个最小 job 把「A40 上到底什么样」测清楚，免得扫档时把多个未知混在一起。

### 2.5.1 第一发（2 CPU / **8 G**）：**OOM 被打死**

```
JAXCHK jax=0.5.3 jaxlib=0.5.3 devices=[CudaDevice(id=0)]   ← A40 上 JAX+CUDA 起得来
SIGLIPCHK 加载耗时=56.7s                                    ← 冷 cache 从 NFS 读 1.66 GB
JAXCHK_EXIT_CODE=137
slurm: Detected 1 oom_kill event in StepId=58530385.batch
```

**8 G 不够**，SigLIP 加载完还没做第一次前向就被杀。这条直接否掉了「1 CPU / 8 G」这类激进档位。

### 2.5.2 第二发（2 CPU / **24 G**，带逐阶段内存埋点）：全绿，一次定准

| 阶段 | `ru_maxrss` | **`cg_anon`** | `cg_current` |
|---|---:|---:|---:|
| 起点 | — | — | — |
| import jax 后 | — | — | — |
| SigLIP 权重后 | 3.77 GiB | 1.81 GiB | 3.93 GiB |
| PosEmb3D 预计算后 | 4.17 | 3.25 | 5.47 |
| MemoryBuffer 就绪 | 4.28 | 3.30 | 5.54 |
| **前向 51 次后** | **20.95** | **8.15** | **11.87** |

拆出来的三个事实：

1. **`PosEmb3D` 预计算独占 0.98 GiB。** `PosEmb3D.__init__` 按 `max_steps=4096` 把三个分辨率的
   位置编码全预计算成 fp32 numpy：`4096×64×768` + `4096×16×768` + `4096×4×768`。
   这块先前完全没算进内存预算里，是第一发 OOM 的主因之一。
2. **前向本身还会再推高约 4.9 GiB anon**（3.30 → 8.15）。51 次就涨这么多，
   是否会平台化必须用真实负载验证——扫档的每 2 秒 `cg_anon` 采样正是为此。
3. **GPU 显存峰值只有 5.03 GiB**（46 GiB 的卡）。显存完全不是约束，
   要压的自始至终是 **host 内存**与 **CPU**。

### 2.5.3 纯 GPU 能力 vs 实际速率：I/O 是 5 倍瓶颈

探针在 `buf.clear()` 后反复前向、**完全不落盘**，测得纯 GPU 稳态：

```
稳态单步 = 10.2 ms  →  98.5 step/s
首次前向（含 XLA 编译）= 132.3 s      ← A40 上的启动开销比本机 ~40 s 贵得多
```

对照真实负载（读写都走 turbo）实测的 **≈19 step/s**：

| 口径 | 速率 | 说明 |
|---|---:|---|
| 纯 GPU（不落盘） | **98.5 step/s** | GPU 的能力上限 |
| 真实负载走 turbo | ≈**19 step/s** | 实际吞吐 |
| 真实负载走本机 NVMe | ≈**67 step/s** | 换成快盘就快 3.5 倍 |

**GPU 有 80% 的时间在等 I/O。** 这既确证了「压 CPU/mem 不会伤 GPU 利用率」的前提，
也意味着**判据②（GPU 利用率退化）在这里判别力很弱，主判据只能是判据①（稳态 step/s）**。

## 三、方法

### 3.1 两段式：本机筛，集群定

- **本机扫档**（`step_bench.sh local`）：不占集群配额，把明显不可行的档位（OOM、
  GPU 利用率塌方）先筛掉，只把 2–3 个候选送上集群。输入刻意用**本机 H5 原件**——
  本机要隔离的是 CPU/内存两个变量，走 NFS 会把 turbo 带宽波动掺进来。
- **集群探针**（`step_bench.sh cluster`）：候选档位各提一个 **1 GPU / ≤00:30:00** 的 job，
  **在 `greatlakes.md` 调试限额内，无需额外放行**。读 turbo、跑 A40，是权威判定。
  它同时回答另一个问题：**NFS venv 的 `jax[cuda12]` 在 A40 上到底能不能起**
  （本仓库是 JAX 栈，集群既往只验证过 torch 栈——这是全流程最大的未知）。

### 3.2 限额怎么做到「真限」（本机实测坑）

| 手段 | 实测结果 |
|---|---|
| `systemd-run --user --scope -p MemoryMax=2G` | **生效**（`memory.max` 确被设为 2147483648） |
| `systemd-run --user --scope -p AllowedCPUs=0-1` | **不生效**——`cpuset.cpus.effective` 不存在，进程 affinity 仍是 `0-31`（user slice 没下放 cpuset 控制器） |
| `taskset -c 0-N` | 生效，语义与 Slurm 给 `--cpus-per-task` 做的 cpuset 绑定一致 |

所以本机档位 = `systemd-run -p MemoryMax` **加** `taskset -c`。该组合已端到端预验证
（含在 tmux 会话里，因为扫档要挂 detached tmux 跑）：

```
$ systemd-run --user --scope -q -p MemoryMax=2G -p MemorySwapMax=0 -- taskset -c 0-1 bash -c ...
memory.max  = 2147483648      # 限内存生效
affinity    = 0,1             # 限核生效
nproc(受限) = 2               # 子进程看到的核数也跟着变
oom_kill    = 0               # memory.events 可读，用于判定该档是否被 OOM 打死
```

另外 `OMP_NUM_THREADS` / `MKL_NUM_THREADS` 必须跟着档位一起改，否则线程超订会把
「档位不够」和「线程打架」两个原因混在一起，档位结论就不可信了。

### 3.3 读数口径（三条，本机与集群共用 `sample_summary.py`）

1. **GPU 利用率跳过前 6 个采样点**。开头那段是 SigLIP 权重加载（1.66 GB pickle → jnp）
   加 XLA 编译，GPU 基本闲着；算进均值会把所有档位一起压低、掩盖档位之间的真实差异。
2. **内存看 cgroup `memory.stat` 的 `anon + shmem`，不看 MaxRSS。**
   `greatlakes.md` 已有铁证：MaxRSS 会**精确贴住 `--mem` 申请上限**（47.71/48、15.77/16），
   那是页缓存填满配额的读数，不是工作集；当年据此推断「48 G 是必需值」正是被证伪的错误。
   `file` 页缓存单列出来，用来解释 `memory.current` 为什么总是贴着上限。
3. **速率取 `build_shard.py` 打印的 `SHARD_DONE ... rate=` step/s**，同一批 episode 同一口径。

### 3.4 速率必须取「稳态」，不能取整体（本机实测）

单进程有一笔**固定启动开销**：载入 1.66 GB 的 `siglip_params.pkl` 转 jnp，再做 XLA 编译。
本机实测四个单 episode 的分片：

| 步数 | 耗时 | 整体 rate |
|---:|---:|---:|
| 514 | 44.2 s | 11.62 step/s |
| 326 | 41.6 s | 7.85 step/s |
| 291 | 41.0 s | 7.11 step/s |
| 239 | 41.5 s | 5.76 step/s |

耗时几乎与步数无关（41–44 s），说明**固定开销约 37–41 s，占了短跑的七成以上**；
按 514 与 291 两点线性拟合，边际约 **0.0148 s/step ≈ 67 step/s**。

结论：**整体 rate 在短跑里几乎全是启动开销，会把所有档位的读数一起压低、
掩盖档位之间的真实差异。** 因此 `build_shard.py` 额外报一个
`rate_steady`（**从第二个 episode 起算**，把首个 episode 的加载与编译排除在外），
`bench_resources.py` 优先取它。整体 rate 仍一并记录，用于核对启动开销本身。

### 3.4.1 扫档期间禁止有大批 NFS 写入在飞（实测踩坑）

本轮实测撞到一次：在 321 GB 的 `rsync 本机 → turbo` 还在跑的时候起本机扫档，
进程 3 分钟只写出 14 个文件后就基本停住。诊断结果是

```
STAT=D   WCHAN=balance_dirty_pages
```

即**被内核的脏页回写背压节流**。rsync 把几十 GB 灌进 page cache 等着写 NFS，
而 NFS 回写只有约 77 MB/s，全局脏页上限被打满后，**连只写本地盘的进程也一起被 throttle**
（脏页限额是全局的，不区分目标是本地盘还是 NFS）。此时 `/data` 所在的 nvme 实测零 I/O，
GPU 也闲着——测出来的任何 step/s 都毫无意义。

**操作规约：本机扫档必须在所有大批量 NFS 传输结束之后再起**，
并在起跑前确认没有别的写入任务在飞。这条同样适用于本地基线构建与 smoke run。

### 3.5 GPU 利用率在本工作负载下判别力有限（预判，待实测确认）

`add_buffer` 每步只喂 1 张图，而每步要写 588 KiB 的 `.npy`；全量 8 分片合计要往 turbo 写
约 283 GB，按该卷 ~132 MB/s 的天花板算，**光写盘就需约 36 分钟**，读 321 GB H5 又约 40 分钟。
也就是说整条流水线**大概率是 I/O 受限**，GPU 利用率本身就会偏低。
所以判据②（GPU 利用率退化 ≤2 个百分点）在这里更像一道兜底护栏，
**主判据是判据①（稳态 step/s 退化 ≤2%）**。实测数据回填后据实修正。

### 3.4 扫描形状

两条一维扫描，不做全笛卡尔积：CPU 与 mem 的瓶颈机理互不耦合（一个卡计算/IO 线程，
一个卡工作集），一维各扫一遍就能定位拐点，成本从 20 档降到 9 档。

- 固定 mem = 32 G，扫 CPU ∈ {8, 4, 2, 1}
- 固定 CPU = 8，扫 mem ∈ {32, 16, 12, 8, 6} G（触发 OOM kill 即判该档不可行）

## 四、选档判据（三条全过才采纳更省的档）

1. **step/s 相对最宽档位退化 ≤ 2%**
2. **GPU 平均利用率退化 ≤ 2 个百分点**
3. **cgroup `anon + shmem` 峰值 ≤ 0.6 × 申请 mem**（留 1.67× 裕度）

任一不过就退回上一档。判据写死在 `step_bench.sh` 的注释与 `bench_resources.py` 的输出里，
不临场放宽。

## 五、本机扫档结果

输入本机 H5、输出 turbo，12 个 episode / 3862 步，每档独立进程。

**第一遍：固定 32 G，扫 CPU**

| 档位 | 状态 | 稳态 step/s | 相对 8 核 | GPU 均值 | anon+shmem 峰 |
|---|---|---:|---:|---:|---:|
| c8m32g | OK | 25.214 | — | 9.44% | 14.94 GiB |
| c4m32g | OK | 26.220 | +4.0% | 9.04% | 12.53 |
| c2m32g | OK | 25.205 | −0.0% | 8.80% | 12.87 |
| c1m32g | OK | 25.887 | +2.7% | 8.57% | 12.45 |

**四档全部落在 ±4% 噪声带内、无单调退化趋势**，GPU 利用率仅漂 0.87 个百分点。
机理清楚：GPU 利用率本就只有 9%，每步的 CPU 活（h5 解压、numpy 像素差、`np.save`）
体量太小，1 核足够喂饱这个节奏。

**第二遍：固定 8 核，扫内存**

| 档位 | 状态 | 稳态 step/s | anon+shmem 峰 | 峰/上限 |
|---|---|---:|---:|---:|
| c8m32g | OK | 26.191 | 13.10 GiB | 41% |
| c8m24g | OK | 26.276 | 12.25 | 51% |
| c8m16g | OK（贴边） | 26.078 | 15.30 | **96%** |
| c8m12g | **内存不足被终止** | — | 11.34 | — |
| c8m10g | **内存不足被终止** | — | 9.08 | — |

**内存才是真正卡住的一维**：12 G 起就活不下来。注意 12 G / 10 G 记录到的峰值
（11.34 / 9.08 GiB）都**低于各自上限**——那是采样间隔 2 秒漏掉了致命尖峰，
**真实峰值只会比记录值更高**。定档必须朝这个方向留余量。

**anon 会不会无界增长？—— 不会。** 时序分位数显示两个 CPU 档都收敛到同一个稳态：

```
c8m32g: 25%→7.99  50%→7.15  75%→7.25 GiB   后半段均值 7.12（前半段 5.45，含启动爬坡）
c4m32g: 25%→10.87 50%→7.13  75%→7.39 GiB   后半段均值 7.16
```

稳态 ≈7.15 GiB，12–15 GiB 是 **episode 切换时新旧 buffer 并存 + JAX 传输缓冲**造成的
瞬时尖峰，不随步数累积。所以 6 万步的全量跑不会因内存增长而爆——
**但内存下限由尖峰决定，不由稳态决定**。

原始数据：`v1-store/bench/local_tier_bench.json`、逐档 `v1-store/bench/<tier>.samples`。

### 5.1 harness 的一个判定缺陷（已修）

cgroup 触顶时 systemd 终止的是**整个 scope**，bash wrapper 自己也被杀，
wrapper 末尾那行 `OOM_KILL=` / `TIER_EXIT_CODE=` 根本没机会执行——实测日志在
shard 起跑行后直接截断、退出码 `-15`。原判定只看 wrapper 打的 `OOM_KILL`，
会把内存不足**误报成普通失败**。已补一条旁证判定：
「被信号终止（returncode<0 或 137）且 stdout 里没有 `TIER_EXIT_CODE=`」⇒ 判为内存不足被终止。

## 六、集群探针结果

四个探针同时提交，**全部零排队立刻起跑**，各 `COMPLETED (0:0)`、耗时 3:28–3:29。
同一批 12 episode / 3862 步，读写都走 turbo。

| 档位 | jobid | jax | 排队 | 稳态 step/s | 相对基准 | GPU 均值 | **anon+shmem 峰** | **峰/上限** | 判据③ |
|---|---|---|---|---:|---:|---:|---:|---:|:--:|
| c4m32g（基准） | 58531760 | OK | 0 | 28.916 | — | 20.57% | 10.50 GiB | 33% | ✓ |
| **c2m24g** | 58531761 | OK | 0 | 28.913 | −0.01% | 21.85% | 10.41 GiB | **43%** | **✓** |
| c2m16g | 58531763 | OK | 0 | 29.168 | +0.87% | 21.56% | 10.72 GiB | **67%** | ✗ |
| c1m24g | 58531764 | OK | 0 | 29.168 | +0.87% | 22.75% | **14.59 GiB** | **61%** | ✗ |

三条结论：

1. **速率与 CPU 无关**：四档 28.9–29.2 step/s，极差 0.9%。GPU 利用率 20.6–22.8%
   （比本机的 9% 高，因为计算节点到 turbo 的带宽更好、GPU 等得少些），但仍有约 78% 时间在等 I/O。
2. **A40 比本机快**：29 step/s vs 本机 26 step/s——不是 GPU 更强（A40 更弱），
   而是计算节点的 turbo 带宽好过工作站。这也说明瓶颈确实在 I/O 侧。
3. **1 核档的 anon 峰值反常偏高**（14.59 vs 其余 10.4–10.7 GiB），同负载同内存、只差核数。
   核数过少会改变分配器/GC 时序、把尖峰推高——这是不选 1 核的实测理由，
   而不只是「留点余量」的直觉。

`gpu_mib_peak` 四档均为 10,091 MiB（46 GiB 的 A40，占 21%），**显存自始至终不是约束**。
