三、关键机制

1. 一卡两个 worker 为什么不用改评估代码

scripts/evaluation/resident_worker.py（9459859 以来没变）在起 server 前用 probe.bind(("127.0.0.1", int(spec.get("port", 0)))) 取一个空闲端口；spec 不写 port，就是让系统分配，同一节点上的多个 worker 不会冲突。控制器 official_queue.py 只按 worker_id 发块，不管 worker 在哪张卡上。所以同一张卡起 wNa、wNb 两个 worker，就是两个独立的领取者。

⚠ 陷阱：端口是先探测、再交给 server 绑定，中间有一段空档。10-31 CC-s42 时，同节点（gl1513）上两个 worker 撞了一次 OSError: [Errno 98] address already in use。一卡两个 worker 时同节点的 worker 更多，撞的概率更高。处置沿用 10-31：用新的 worker-id 在同一张卡上重起（控制器会拒绝重复使用旧 id），不改代码。

2. 测速怎么做（V5）

第 1 次正式运行 N-s42：A 份占位（65209321）每卡 1 个 worker，--cpus-per-task=4，共 4 个；B 份（65209330）每卡 2 个，--cpus-per-task=2，共 8 个。12 个 worker 从同一个队列领块，跑完 800 局后，按每局 accepted 记录的 worker 归属和完成时刻，分别算两份占位的稳态吞吐（局/小时，去掉每个 worker 的第一块，因为第一块里有 JIT 编译）。

  • B 份吞吐 ≥ 1.15 × A 份 → 后五次两份占位都改成每卡 2 个 worker（共 16 个）。
  • 否则后五次都用每卡 1 个 worker（共 8 个）。
  • B 份出现以下任一情况 → 判定每卡 2 个不可行，后五次用每卡 1 个，且优先于上面的 1.15 倍判据：① B 份 worker 处理的局在队列重试 1 次后仍为 error；② B 份 worker 日志出现 Killed 或 out of memory。同节点撞端口（Errno 98）按 §三.1 换新 worker-id 重起的，不算。
  • V6 照旧要求 errors=0：第 1 次运行若最终 errors>0，V6 如实记 FAIL，其余 5 次照跑，最后一并汇报。

把测速放在正式运行里不影响成绩：每局的环境由 test 元数据固定；模型采样噪声取决于 server 的 seed 和这个 worker 依次领到了哪些局，原本就随动态队列变，worker 布局和以往一样不进入成绩口径。

3. 时间与占位余量

10-31 实测 10 卡每卡 1 个 worker，800 局约 85 分钟，即约 14.2 卡·时/800 局。8 卡每卡 1 个 worker 时约 106 分钟/次；每卡 2 个 worker 如果有 1.3–1.6 倍收益，约 66–82 分钟/次（未实测）。6 次运行加冒烟和换根间隙，合计约 7.5–11.5 小时。

占位分别在美东 11-09 13:38、14:04 到期。现在是 11-08 16:06，训练的 V10 还没做完，所以余量取决于它什么时候交出占位。规则：每次起一轮新运行前，算剩余时间是否 ≥ 1.2 × 上一次实测单轮时长；不够就不起这一轮，汇报你，由你决定是新提交单卡占位（份数由你定）接着跑，还是到此为止。按 K5 的交替顺序，两个模型完成的 seed 数最多差 1。

4. 占位交接（要你出面的一步）

训练会话的 V10 写着「两hold释放」，它做完严格恢复会按规则逐个 scancel。跨会话消息不能算你的授权，所以这一步要你自己告诉训练会话：V10 完成后不取消 65209321、65209330，在它的 current.json 里写明占位已转交 gl-abl-encoders-eval。本任务开工前会现场核对：上游是 done、两份占位都还是 RUNNING、上面没有训练会话残留的 srun step（squeue -s）。如果占位已经被取消，本任务停下来问你。
