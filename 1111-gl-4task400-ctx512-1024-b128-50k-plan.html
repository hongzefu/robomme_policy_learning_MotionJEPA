2. 关键机制

2.1 梯度累积（新写代码，训练链路改动）

为什么非改不可：仓库训练代码没有累积开关（grep -iE "accum|microbatch" 对 scripts/training/train.py、src/mme_vla_suite/training/*.py 零命中）。A100 4 卡 context 512 b128（每卡 32）实测峰值 73,005～73,019 MiB/卡（docs/training-doc/ctx-stock-scaling-20260928/result.md），A40 只有 48 GB；GL 4×A40 每卡 16 的 context（1101，带 motion）峰值 38,489 MiB，装得下。

锚点：scripts/training/train.py::train_step（当前一次 nnx.value_and_grad → state.tx.update）；src/mme_vla_suite/training/config.py::TrainConfig 新增字段 grad_accum_steps: int = 1（CLI --grad-accum-steps）。

# 伪码（train_step 内）
B = batch_size; K = grad_accum_steps; m = B // K
micro = tree_map(lambda x: x.reshape(m, K, *x.shape[1:]).swapaxes(0, 1), batch)   # 第 i 个 micro = 样本 i::K
def body(acc, (i, mb)):
    l, g = value_and_grad(loss_fn)(model, fold_in(train_rng, i), *mb)
    return (acc[0] + l / K, tree_map(lambda a, b: a + b / K, acc[1], g)), None
(loss, grads), _ = lax.scan(body, (0., zeros_like(grads)), (arange(K), micro))
updates = tx.update(grads, ...)          # 每个优化步只更新一次，步数语义不变
# K == 1 时走原代码路径，一字不改

⚠ 陷阱：不能直接 reshape(K, m)。batch 在 FSDP 数据轴上按 dim0 连续切给 4 张卡，reshape(K, m) 会让第 0 个 micro 只落在前 2 张卡上，另两张空转且显存不降。必须 reshape(m, K).swapaxes(0,1)，让每个 micro 的 64 个样本均匀分布在 4 卡（每卡 16）。

⚠ 陷阱：flow-matching 的噪声 / 时间步按 rng 与 batch 形状采样，K=2 与 K=1 的噪声不同，做不到逐位一致。等价性按 AGENTS.md 第 18 条分层验收：K=1 对旧代码逐位一致；线性性在玩具 loss 上逐位验证；真实训练 K=2 对 K=1 只要求数值容差内的行为一致（§3 V2–V4）。

仓库只有 context 的 8frame（512）与 32frame（2048）yaml；src/mme_vla_suite/training/framesamp_dataset.py 的形状守卫只放行 legacy 形状与 raw == (2048, 64, 1) 的 context，1024（16 帧 × 64 token）会被拒绝。改法：

六 风险登记

风险处置
spgpu 排队久（4 卡 × 14 天）开工即提交，排队与改代码、下载并行
ctx1024 每卡 16 OOM每卡 8 × 累积 4（同规模，自行继续并告知）；仍 OOM 停
ctx1024 实测步时 > 336 h按 5000 步 ckpt 换新占位续跑（第 2 条 5 倍内，告知）
turbo NFS 读速拖慢冒烟记 util 均值，明显低于 90% 记「性能异常」交你，不擅改 worker 外的口径
bf16 跨卡型（A40 对 A100 的 modulation 对照）不逐位只比成功率，不比数值
bucket 子集 include 模式写漏先 --dry-run 列清单，对照 _train_common.sh 必需路径再下
