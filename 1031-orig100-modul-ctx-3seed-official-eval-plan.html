2. 三个 seed 是哪三个、seed 管什么

  • 官方 seed = 7、42、0。证据一：benchmark 官方提交模板 third_party/robomme_benchmark/doc/submission/model_example.md 写「require at least three runs with different random seeds……The benchmark seed is fixed internally」，结果表头 Seed 7 | Seed 42 | Seed 0 | Avg。证据二：官方训练仓库副本 /data/hongzefu/robomme_policy_learning-memER/scripts/compute_results.py 的 --seed_list 默认 seed0,seed42,seed7。论文正文没有列出 seed，本地也没有 PDF，这一点未核实。
  • seed 只管模型采样噪声：server 端 serve_policy --seed → policy.py 在 reset() 里 self._rng = jax.random.key(self._seed)。环境局由 test 元数据 records[].seed 固定（benchmark readme「All seeds are fixed for benchmarking」），所以三个 seed 跑的是同一批 800 局。
  • 不要和项目早期 docs/training-doc/eval-3seed-context-vs-motion/ 的 42/7/2024 混淆：那是自己的 4 任务口径。
  • ⚠ 官方 compute_results.py 默认还对 3 个 checkpoint（60000、70000、79999）取平均，std 用 pandas 默认的样本标准差（ddof=1）。本计划按 K2 只评 59999，std 只来自三个 seed，比论文少了 checkpoint 这一维的方差；报告里会写明这一点。

3. 为什么必须改代码、改多少

seed 的传递链路本来就通：spec 的 model_seed 字段 → resident_worker.py::server_command 拼 --seed，client_command 拼 --model-seed（缺省 42），客户端首包核对 server 回显的 model_seed。唯一的阻塞是官方 profile 把 seed 写死成 42：

# examples/robomme/eval.py::evaluate（9459859）
elif (args.dataset != "test" or args.max_steps != 1300 or ... or args.model_seed != 42):
    raise ContractError("官方评估固定 test、1300、16 步和历史模式，RPC 超时须为正")

改法：把 args.model_seed != 42 改为 args.model_seed not in (0, 7, 42)，错误信息同步写明「seed 须为官方 0／7／42」，并加一条定向单测。scripts/evaluation/manifest.py 与 check_runtime.py 里的 42 只用于生成 validation 身份和 runtime 合同的模型检查，不在官方评估链路上，不改。spec 里新增 "model_seed": <seed>，run 身份 run-identity.json 的 model_seed 写对应 seed，所以 5 次运行的 run_identity_sha256 互不相同。

改动在新分支 v4-eval-3seed-1031（从 9459859 分出）上做，因为当前分支 v4-eval-official-1026 没有 mme_vla_suite_orig16_b128_60k 配置。C-s42 用的是 9459859；新跑 5 次用新 sha，两者差别只有 eval.py 的 seed 判断（含一个模块常量与错误信息）和一个测试文件（K3 复用的依据）。

4. 排队与资源

同一时刻只跑一个 run 根，10 个 worker 都挂在它上面；一次 800 局跑完（控制器 COMPUTE_DONE、worker 自然退出），换下一个 run 根，在同样的 10 份占位里重新 srun 起 worker。冒烟只用 10 份中的 1 份，其余 9 份空等约 20 分钟；冒烟通过后 M-s42 用全部 10 个 worker 起跑。10-29 实测 10 卡 800 局约 1 小时 28 分，5 次合计约 7.5 小时，加上换 run 根的间隙约 8～8.5 小时。占位承诺 10×48 = 480 GPU·h，实际占用约 85 GPU·h，跑完立即释放。

5. 实施中调整（2026-10-31 美东，开工令之后、动手之前，待用户重新认可）

用户原话：「优先先跑 modulation，现在同样的 seed42，然后再跑其其他的两个。」理解为 modulation 三个 seed 先跑（seed 42 最先，再 7、0），context 的 seed 7、0 放到最后。旧顺序 C-s7 → C-s0 → M-s42 → M-s7 → M-s0 改为 M-s42 → M-s7 → M-s0 → C-s7 → C-s0。

随之改两处：① 冒烟从 5000 步改为直接用 59999：modulation 排第一后冒烟就在关键路径上，改用 59999 省掉一份约 12 GB 的下载（约 20～30 分钟）；开工前已核实 5000 与 59999 除 checkpoint 外的 17 个根文件 sha256 逐个相同（motion_provenance.json 均为 d135718b…），runtime 合同用 59999 生成、冒烟与三个 seed 共用。② 冒烟期间不再同时跑 context，其余 9 份占位空等约 20 分钟。总局数、占位数不变。

开工前一致性审查 PLAN_CONSISTENCY_REVIEW=FAIL base=e60dd99 findings=4 blocking=2 的处置：F1（阻塞）SEED_ECHO 要读的 model_seed 不在逐局记录里——改为用 spec、run 身份与逐局 run_identity_sha256 三处比对（见验收表），不改代码，需用户认可这一判据改法；F2（阻塞）占位份数口径——统一为 10 份、cancelled=10；F3 合同来源——写定用 59999 生成、共用；F4 措辞——已统一。

六、风险登记

风险处置
modulation 在 server 侧恢复失败（融合类型或 dim 与配置不匹配）冒烟暴露；M-* 暂停，交用户裁决是否先跑 C-*
seed 0 在某处被当作「未设置」走缺省 42（spec.get("model_seed", 42) 对 0 没问题，但其他地方若写 or 42 会出错）冒烟用 seed 0 并要求 server_seed=0；SEED_ECHO 再逐局核
ControlMaster 掉线先问用户 Okta 方式再重建；队列支持 worker 重连
换 run 根间隙浪费占位时间上一 run COMPUTE_DONE 时即初始化下一 run 根，间隙控制在 10 分钟内
spgpu 排队可用占位不足 10 份时先用已到手的跑，不等齐

七、盲区诚实清单

  • 官方 seed 7／42／0 来自提交模板与 compute_results.py 默认值，论文原文未列 seed，未从 PDF 核实。
  • 论文 std 可能还包含 3 个 checkpoint 的方差，本计划只有 seed 方差，两者不完全可比。
  • C-s42 与新 5 次用的执行 sha 不同（只差 seed 判断一行）；如用户要求严格同 sha，按 K3 重跑。
  • 10 个 worker 并行的稳态吞吐对 modulation 未实测，时长估计按 context 的 1.5 h／800 局。
