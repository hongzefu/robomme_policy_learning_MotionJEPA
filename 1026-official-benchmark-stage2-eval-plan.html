三、motion 与训练一致，靠的是窗口定义而不是“每 16 步算一次”

令 D=exec_start_idx 为真实 demo 帧数，全域当前帧号为 t，执行段当前索引为 q=t-D。首包送入全部 demo 加执行第 0 帧；之后每执行 16 动作送 16 个新帧。训练样本覆盖每个 exec t，不只每 16 帧；推理只是按官方动作块节奏调用。

FrameSampMemory::_encode_ready_windows 与 motion_store::visible_motion_rows 都使用独立的 demo／exec 网格：窗口 W=33、步长 S=32；demo 起点 32m 至少有 17 个真实帧才保留，不满 33 时重复 demo 最后一帧；exec 起点 D+32m 必须满足 32m+32≤q，绝不尾补、跨段或偷看未来。

k_demo = max(0, floor((D - 17) / 32) + 1)
k_exec = max(0, floor((q - 32) / 32) + 1)
q = 0, 16, 32, 48, 64  →  exec 窗口数 = 0, 0, 1, 1, 2
窗口总数 = k_demo + k_exec ≤ 96；超过即报错，不能截断、抽稀或临时改预算。

第二种 padding 是容量 padding：不足 96 个 motion token 时，motion_emb 和 motion_pos 右侧填零，motion_mask=False，时间填 2147483647；合法 demo 尾补产生的 token 则 mask=True。两种 padding 不可混用。

每个窗口从 33×256×256×3 uint8（6,488,064 字节）经固定 VAE 得 (9,16,32,32) float32（589,824 字节），再由 epoch105 的 EMA encoder 得 (1,4,256)，按 slot 顺序串接成一个 1024 维 token（4,096 字节），不均值、不做 L2。视觉路为 8 帧×64=512 token，motion 路为 96 token，总容量 608。

训练与推理同时导入 shared/sampling.py::memory_order，按 2×全域起点+kind 稳定排序：frame 的 kind 为 0、motion 为 1，同刻 frame 在前。motion 位置码取窗口起点的 pos_emb[f,0,:pos_dim]；进入既有 motion MLP／位置投影与 modulation，保持 mask 语义。推理必须 train=False，无训练增强与 dropout。

五、弹性 job 池动态领取，运行中可增减数量

每个 worker 只在自己的占位 job 内启动一个常驻 server 与 sidecar；领取一个 5 局 chunk 后，启动独立官方 eval 仿真子进程，结束即回收仿真资源，再领下一块。固定 round-robin 混排 16 任务，无需预跑估计长短；模型阶段依次推进，worker 不跨模型阶段抢任务。

target_jobs=N 必须显式提供，没有固定默认值。运行中的 desired_jobs 与 pool_revision 是可变控制状态；扩容在已批准包络和配额内增加job，让新worker领取ready；缩容先停止被选worker领取，封口当前局、归还未开始局，再清理该pool明确登记的step／JobID。PENDING与UNKNOWN也占资源账本，不能因未见RUNNING而重复申请。

NFS 不引入数据库：不可变清单、原子 mkdir claim、临时文件加 rename 提交结果。claim 后尚未写 owner 就崩溃也必须可识别。heartbeat 只诊断，不按 TTL 抢活 worker；唯一控制器先确认对应 Slurm step 已终止，再提升 generation 重发。旧 attempt 永远不能覆盖 canonical。

success／fail／timeout 为正常终局，不自动重跑；基础设施 error 最多一次同 seed 重试，先确认旧 step 死亡。48 小时预算到期 drain 并保留队列，不超批准资源包络扩容，也不自动续批。建议每局墙钟上限 2,400 秒，5 局块加启动清理 1,800 秒得 13,800 秒=3小时50分；这是待实测的运维上限，与官方 1300 动作语义分开。

EpisodeEvaluator::init_episode 设置 D=len(initial_front_frames)-1，最后一帧是 exec0；首个 add_buffer 发送 D+1 帧。utils::pack_buffer 只打包 front 为 (T,1,256,256,3) uint8，state 为 (T,8) float32，携带稳定的 exec_start_idx=D。

合法首包必须一次包含完整demo与exec0，即全域 0…D 共D+1帧；partial demo首包直接拒绝，不能先编码demo尾窗再补后续demo。任意拆包／单帧等价测试仅作用于首包之后的exec新增段，正式调用仍按官方16帧节奏。

这里的frame-id／t／D是官方wrapper实际返回的观测序号，不是物理仿真step计数。官方可能过滤 NO RECORD、在reset内执行 init_action，或在terminal路径递归step；这些行为保持不变。对拍fixture须同时记录wrapper输出序号、底层step trace、过滤标记、reset初始动作与terminal递归，并核front／wrist／state逐项对齐，不能把未返回的物理步补成历史帧。

get_action_chunk 先 add_buffer，再 infer；infer 输入当前 front、wrist、8 维 state、任务 prompt。采用与训练配置匹配的 history 模式，默认不启用 subgoal predictor 或 MemER，不能因某任务失败临时注入 oracle subgoal。

模型 action horizon 为 20，返回 (20,8)；官方 exec_horizon=obs_horizon=16 只执行前 16。action 的剩余 4 步不跨 chunk 复用；清空已提交的历史批次后，每步新增观测，下一次 replanning 提交恰好 16 新帧。

1.3 seed 是两条不同的链

模型 seed=42 必须由 server CLI 传到 create_trained_policy，由 metadata 回读确认。官方 eval 的 model_seed 原本主要用于结果目录命名，仅改 client flag 并不会改变 server RNG；这必须在启动握手中显式拦截。

仿真 episode seed 由官方 test episode／builder 的既有映射决定，不能把 model seed 42 覆盖给所有环境。清单同时记录 model_seed 与官方 episode 身份，任何重试保留两者。每局 policy reset 复原该模型 seed 的 RNG 状态，使队列顺序不会改变同一局的初始模型随机流。

1.5 健壮性修复不改变成功路径

固定官方代码中的风险拟修复位置与方式必须证明未变的行为
make_env 在 episode 的 try 外evaluate 将创建、reset、rollout、finally close 纳入单局异常边界，初始化失败落到该 episode 的 error。同一官方 episode、builder 参数与成功 rollout 顺序不变；不因初始化失败换 episode。
step 异常后返回 obs=None，上层可能二次解包异常eval_each_episode 先识别 env error 与观测缺失，保留原始异常；正常路径保持官方 timeout 检查顺序。第 1300／1301 步 success／fail／timeout 的 trace 完全一致。
含字符串 "error" 的结果参与 sumtyped result schema；controller 单独计 success、fail、timeout、error 和 coverage。完整无 error 时，16 个成功率均值等于成功总数／800。

1.6 RPC顺序、不确定响应与单会话占用

每局新建 episode_nonce；历史包记录 batch_seq、first_global_frame、帧数与 payload_sha256；infer记录 replan_seq，与刚确认的历史末帧绑定。server在写memory或推进RNG前核会话身份、包序、帧域和payload；客户端日志与server审计逐项可对齐。这是顺序验证，不设计复杂跨断线ACK缓存。

任何reset／add_buffer ACK或infer response不确定时，禁止在原局重发，也禁止沿用可能已改变的memory／RNG继续。结束该attempt，确认旧client子树已退出，server内旧RPC及sidecar均静止；不能证明静止就重启server与sidecar。之后才可同官方episode、同seed整局重试最多一次，重试预算按episode持久累计，worker／server重启不清零；正常success／fail／timeout不重跑。

一个server同时只允许一个活动attempt会话。第二连接须在reset前拒绝，即使run identity和server nonce相同，也不能并发reset另一个episode。只有旧client子树退出并解除服务端活动会话后才能接入下一client；断线不自动视为会话已释放。RPC故障注入须覆盖已执行但ACK丢失、infer已推进RNG但response丢失、旧client迟到与并发连接。

首版恢复采用简单一致的边界：普通chunk结束只退出sim；发生infra／不确定RPC时，worker尽力封口已有terminal与错误记录，然后退出整个resident step（client／server／sidecar一并停止），不等待下一块。controller确认该step终态后才决定重发，避免“controller等step死、worker等下一块”的死锁；停止按事前固定grace执行有界TERM→KILL，无法确认静止就不重发。

2.3 两种 padding、位置码、mask 与交错

像素尾补发生在 VAE 之前：重复 demo 末帧的完整原始 uint8 像素，保持训练预处理；验证每个 pad 槽与末帧 SHA 完全相等，记录真实帧数和 pad 数。编码后该窗口是有效内容，motion_mask=True。

容量 padding 发生在 token 装配时：motion_emb=(96,1024) float32、motion_pos=(96,pos_dim) float32，不足部分全零；motion_mask=(96,) bool 有效前缀为 true。时间使用共享 pad_times 的 sentinel，不拿零伪装不存在的时间。

motion position 来源于窗口起点 f，对应 store.pos_rows(f)[:,0,:pos_dim]／在线 pos_emb[f,0,:pos_dim]，不是尾端、中心或 q。视觉 frame 的每个图像 token 保持自身内部顺序，motion 四个 slot 已先 concat，只有一个时间位置。

shared/sampling.py::memory_order 将 512 visual 候选位与 96 motion 候选位拼接，按 time×2+kind 稳定排序。相同时刻 visual 在 motion 前；同帧 64 个视觉 token 内部不换序；padding 排到尾部，同为 padding 时视觉在 motion 前。必须核 mem_order 是 0…607 的完整置换。

模型既有 motion MLP／位置投影对 1024 维输入变换，随后与视觉 memory 按同一置换交错，沿现有 modulation 分支进入 VLA。mask 的有效性、顺序和冻结语义原样沿用训练；不能因为 pad 像素存在就把合法 motion token 屏蔽，也不能把全零容量位当有效 token。

2.4 reset、输入拒绝与实时调度

MME_VLA_Policy::reset 与 FrameSampMemory::clear 每局清空帧、token、段边界、网格起点和模型 RNG；sidecar 中只保留 VAE／encoder 模型及经核验的静态来源，不能留上一局窗口缓存。reset 的 ACK 是下一局首包前置条件。

输入检查覆盖重复全域帧号、段边界漂移、乱序／缺帧、跨段、未来帧、错误 uint8 尺寸、负索引与 4096 位置越界。批次必须先完整校验再写状态，失败不能留下半个 exec_start_idx 或部分 raw frame。现有检查不足的项目以最小补丁补齐并负例验证。

模型重规划每 16 动作，motion 成熟网格每 32 帧，这两个节奏独立：q=16 时没有 exec token 属于正确行为；q=32 时必须立刻出现首个 exec token，不能滞后一包到 q=48。训练对所有 exec t 取样，推理验证既测边界 t，也测真实 16 帧批次。

2.5 全官方预算扫描

阶段 I 静态核 16×50 manifest，不为了预算先跑 800 次 reset 来阻塞组件验证或阶段 II 排队。正式每局官方 reset 完成后、第一步 action 前读取真实 D，按 q=1301 保守计算 k_demo+k_exec≤96 与 D+q<4096；失败即阻断该局和后续正式运行，不截断。全部 800 局完成后汇成全量预算报告。

实际最后重规划通常 q=1296，与保守 q=1301 的 exec 窗数均为 40；报告同时列实际与保守上限，避免混淆帧号和张数。若官方元数据本身能给出真实 D，可提前静态核；不能用估计 D 冒充真实值。

历史 Dmax=1247 的演示得到 39＋40=79 motion 窗；q=1300 时最大全域帧号为 2547，若从 0 连续记录则观测张数为 2548。该数字不是此次官方新实测；只有覆盖全部 800 局的独立报告可以签发 OFFICIAL_BUDGET=PASS。

任何 episode 超过 96 或位置 4096 都是该局第一动作前的阻断。不能通过丢早期 demo、缩短 rollout、均匀采样 motion、改 stride／预算／position table 或改 checkpoint 来绕过；需要用户审查新的训练兼容方案。

3.3 拟新增 eval_target_contract.json

身份分层避免 SHA 循环，也避免60k尚未到位阻塞阶段I组件验证或阶段II排队。runtime_contract.py 规范化所有 descriptor：motion_identity_sha256 只绑定 MJ／VAE／source_pin／软件数值／fixture／阈值；A40 证书绑定 motion identity 与验证代码 SHA。model_identity_sha256 在 60000 到位后绑定 VLA 文件 SHA、resolved config、normstats 与 motion identity；最终 run_identity_sha256 再绑定 model identity、证书 SHA、benchmark／metadata／seed／eval 参数。证书不反向绑定 final run SHA。

阶段I（或阶段II首个hold补验）的早期同架构checkpoint单独生成 validation_model_identity_sha256 与 validation_run_identity_sha256，绑定早期checkpoint真实文件SHA、resolved／normstats、motion identity与有效推理配置；server通过标准 run_identity_sha256 字段传递验证run身份。验证目录、purpose与结果母集独立，仅用于组件数值验证与profile，不能进入正式60000的accepted或score；正式model／run身份仍等60000完整到位后生成。

“同架构”不能只比较shape：验证checkpoint必须与当前训练已锁定的有效推理配置相容，核history预算、窗口／stride／padding、图像变换、参数与输入dtype、num_steps=10、动作horizon20／执行16及motion identity。60000到位后对其实际resolved再复核这些字段；不相容就不能沿用早期数值／资源证据，重新确定受影响门，而不是只换权重路径。

schedule_identity_sha256 单独绑定训练run、目标step=60000、eval代码、benchmark、单job规格与motion identity，用于T−2h调度意图与ledger；不依赖VLA60k文件、A40证书或final run SHA。worker数量／ID不进入model／run评估身份；desired_jobs、pool_revision、membership与已批准资源包络另列可变控制账本，调N不创建新评估或新schedule意图。排队和正式launch仍是两条门槛。

pool_id 与 schedule_id 是创建调度意图时分配并持久保存的稳定ID，不由code／CPU规格／motion SHA派生。上面的schedule SHA只标识该意图的一版descriptor；代码／规格／证据修订通过revision追加并沿用同一pool ledger，不能因SHA改变开新账本再申请一批job。任何新run绑定此pool时先对账既有所有slot_instance，避免修订后重复占资源。

3.4 设备与进程身份

Slurm 单 GPU step 的 CUDA_VISIBLE_DEVICES 是分配 token，可能是物理序号或 UUID；不得覆盖成训练 snapshot 的 4，也不能假设物理 0。worker 将分配 token 传给新暴露的 --motion-online-gpu，sidecar 在自己的可见设备域内使用逻辑设备 0，并回报真实 GPU UUID。

握手核对 JobID、StepID、worker UUID、server PID、sidecar PID、CUDA 可见 token、GPU UUID、模型 seed、VLA SHA、motion 合同和 eval_target 证书。server metadata 的标准字段为 run_identity_sha256、server_nonce、model_seed、model_kind；client 必须提供 expected_run_identity_sha256 与 expected_server_nonce。只在内存配置副本覆盖设备；训练 YAML、离线 store 与原证据保持只读。

同一 GPU 上 JAX server、PyTorch sidecar 和仿真显存竞争仍未知。预分配设置、allocator、precision 必须写进目标 runtime 并固定后测试；OOM 时停止，不临时减 dtype、budget、图像大小或改动作 horizon。

五、动态队列：身份、持久化与崩溃边界

5.1 一模型一阶段与稳定混排

当前只评估当前 Stage2 motion VLA 的 60000 checkpoint。清单可为未来经用户指定的多个模型保留顺序配置；当前模型全部已接受或明确停止之前不开放其他模型，worker 不跨模型偷取，server／sidecar 因而常驻。

先以 episode 编号为外循环、官方 task 顺序为内循环生成 800 项，再每 5 项切块，得到 160 块。这个固定 round-robin 让不同任务交错，不依赖事先知道耗时；每块内可跨任务，因此仿真进程每局创建并关闭对应 builder 环境。

任务身份至少绑定 model_id、VLA checkpoint 完整 SHA 清单、config SHA、model seed、benchmark commit、episode manifest SHA、eval code commit、目标合同 SHA。chunk_id 还绑定成员序列；attempt_id 再绑定 generation、attempt 编号、JobID／StepID、worker UUID。输出目录名称不是身份凭据。

5.3 claim、owner 与不可见窗口

worker按稳定chunk顺序向唯一controller请求claim；controller在串行事务内先核pool状态／revision／成员资格，再执行 mkdir(queue/claims/chunk_id) 并授予唯一attempt，worker不能绕过冻结状态自行mkdir。owner以临时文件rename发布，含task identity、generation、attempt_id、worker UUID、slot_instance、JobID incarnation、StepID、PID与hostname；mkdir后owner前崩溃仍按下述ownerless规则处理。

claim授权本身使用持久 claim_request_id 幂等：每个slot_instance最多一个未终态assignment，同一请求重试返回原grant与同一attempt。若授权回执丢失，worker先query原grant，不能改request_id再领新任务；未查清之前保持原assignment占用。负控注入“controller已授予但回执丢失”，确认重试／query只返回同attempt且不会产生第二个未终态assignment。

mkdir成功而owner未写的崩溃窗口必须单独处理。控制器将其标为ownerless，关联启动登记、Slurm step与日志；不能因空目录、mtime或heartbeat超时抢占。无法唯一归属时保留claim，冻结本pool的membership快照并暂停扩缩容，drain快照内全部相关worker steps（包括已标retiring但尚未确认终态者）；确认全部相关step终态后才generation++重发未提交局，再恢复伸缩。不能只检查当前RUNNING个数；恢复复用已登记hold，并计入重试上限。

worker 的 heartbeat 可记录当前 episode、最近动作步、last_progress、PID 与资源，但只用于诊断。慢仿真、NFS 暂停、模型编译或日志停更不等于进程已死；TTL 不构成重试授权。

5.4 单控制器、fencing 与唯一接受

controller_host 固定为aspen或vail中的一台，使用宿主进程生命周期锁＋NFS审计记录取得唯一写权。提交、launch、resize、claim授权和回收由该controller串行事务驱动；不做自动跨机主备、不按TTL抢锁，换主必须确认旧主已退出。进入 RECOVERING 后冻结submit／launch／resize／claim，记录pool_revision和全部相关slot_instance；包含SUBMITTING、UNKNOWN、STARTING、DRAINING、CANCEL_REQUESTED，不能只看RUNNING。

恢复逐slot核JobID的incarnation（提交标识／开始时间等，防JobID复用）、StepID、进程身份和终态。UNKNOWN未对账、任何旧RPC／sidecar未静止或pool_revision已变都不能换代；全部旧实体已排除且revision仍匹配才发布新generation并解除冻结。worker可写文件只作输入，canonical必须由控制器校验后生成自身不可变描述符；控制器不会以worker仍可改的文件为权威。

恢复事务顺序固定且可重放：①停止旧执行并确认client／server内RPC／sidecar／step静止；②先接收旧generation已经封口的正常terminal；③持久记录每个原episode的已终局、未开始、未确定项与累计retry；④才generation++并发布余项ready，旧claim留审计。首次infra error只进入attempt错误账本，不占canonical；增加generation不能替代停止旧执行，也不能让尚可接受的旧代正常终局因换代被丢弃。

worker仅写自己的attempt目录，不直接写canonical／accepted或总表。环境终局一确定，先原子持久化小型不可变 terminal_outcome（身份、seed、step、success／fail／timeout、RPC序号）；视频／日志关闭与SHA随后作为独立 artifact_receipt。controller分别核验并生成execution与artifact接受描述符；chunk清单只是汇总，不能成为单局已完成的唯一入口。崩溃块的已持久终局在确认旧执行实体静止后仍可接受。

canonical 建议以 os.link(控制器生成的不可变descriptor,唯一目标) 原子创建且拒绝覆盖，先在目标 NFS 挂载验证硬链接原子性；源descriptor由控制器核验后生成并封存，不能链接worker仍可修改的结果文件。即使单控制器也不能用 replace 覆盖已存在 accepted。完成以逐集 canonical 集合为准。这里只保证权威结果一次，不承诺故障条件下物理计算恰好一次。

发布后故意修改worker原结果文件的负例中，控制器canonical内容必须不变；artifact引用按已记录SHA重新读取时必须发现不一致并标artifact_error。不能把“descriptor未变”误当作被引用视频／日志也不可变。

旧 attempt 在被 fencing 后到达，仍保留为可追溯隔离证据，不能覆写 canonical。若 controller 在接受记录发布后、总表更新前崩溃，重启从 accepted 重建总表；总表不是真源，避免“写总表一半”丢失局。

5.5 部分完成、错误与一次重试

若第三局崩溃，前两局已持久terminal必须保留；视频、磁盘或close失败不能触发policy重跑，只能补交已经采集的产物，无法恢复标 artifact_error。若环境可能已终止但terminal尚未持久即崩溃，显式记 uncertain_terminal，不得掩饰可能发生的物理重执行；如继续，只能在episode全局一次重试预算内并保留不确定记录。其余未开始局归还ready，母集不变。

正常success／fail／timeout不自动重试。无已持久terminal的infra error（含不确定RPC）最多同seed整局重试一次，预算按episode持久累计，不因换worker／server重启清零。重试前排除合同错误，并确认旧client子树、server内旧RPC、sidecar全部静止；不能证明则重启server＋sidecar。确定性合同、超预算、来源与数值失败直接阻断，不当可重试小故障。

重试仍失败时保留终态 error，coverage 仍包含该官方 episode；队列可以停止并给出不完整诊断报告，但正式 OFFICIAL_SCORE 不成立。不能删除 error、替换随机种子、另抽 episode 或将它悄悄算作普通 fail 后宣称完整有效。

5.6 何时等待、完成与 drain

若无ready但有running／claim／待接受结果，idle worker短退避等待。分开报告 execution_coverage 与 artifact_coverage：800局唯一accepted终局、无未决generation／attempt才完成执行覆盖；完整交付另要求产物齐全，或用户明确接受具体缺失并保留artifact_error／例外。正式score不能删除error提高分母外成功率；未解决execution error不发布完整score，artifact缺失状态也必须随报告公开。

接近占位 48 小时边界时设置 drain：不再领取预计无法在剩余预算内完成的新块，现有 episode 按明确 deadline 收尾，尚未完成的清单保留。该轮不自动新建或续期占位 job；续批需要用户新授权。

每个hold按自身Slurm StartTime／EndTime计时，不等所有目标N同时RUNNING；已就绪的席位可先完成门禁并工作。自然TIMEOUT／48h耗尽不能触发按desired_jobs自动补一个新48h job，续批须新授权。提交前固定本campaign累计 gpu_hour_limit 与绝对 deadline，按各hold实际占用累计并预算未完成工作；缺预算不自动提交，扩容也不能突破该累计上限或截止时间。

容量预估按每个hold实际EndTime、剩余episode与profile耗时计算，扣除启动／封口／清理余量；NFS冷启动并发必须有限并记录上限，避免同时加载多个模型使首轮profile失真。48h只是单hold上限，不保证完成800局。出现ENOSPC时停止领取并保留终局／错误账本，不能反复重算来尝试解决磁盘不足。

建议 episode_wall_seconds=2400、startup_cleanup_seconds=1800，则 k 局块上限至少 k×2400+1800；k=5 为 13,800 秒。这是 chunk deadline，不是持久 worker／srun 的总寿命；resident step 按 hold 剩余 48h 管理。旧固定 14,400 秒不得不加说明地复用成全局 worker 上限。

wall deadline 是基础设施保护，触发应记录 infra error／中断原因，与官方动作步数 timeout 分开。初始单 job profile 若显示合法慢进展超过建议值，应先审资源与阈值，不能在正式批次中悄悄缩短或长时间误杀。

5.7 弹性资源池的扩容与缩容

target_jobs=N 是启动时必须提供的目标；运行中用 desired_jobs 表示目标容量、pool_revision 表示控制状态版本。通常N≥1；显式将目标设为0只表示全池drain，尚未覆盖的评估仍未完成。控制器是唯一伸缩写者，每次变更校验expected revision，并记录发起原因、前后N、批准资源包络与实际配额。

扩容先对账RUNNING、PENDING、SUBMITTING、UNKNOWN和retiring资源，确认所需增量没有被既有提交覆盖且不超资源包络，再创建唯一submission_id并提交。新job到位后逐台完成GPU／runtime／证书与server身份握手，成功后加入同一个ready队列。新增节点不能继承另一节点的现场GPU／driver检查；人数变化不改变任何episode seed、model/run身份或accepted集合。

slot_instance 与 launch_id 永不复用，GPU初始化之前先取得该launch的独占启动许可并再次核pool状态／revision。迟到srun不能绕过RECOVERING；Slurm requeue即新的执行incarnation，必须重新登记并做节点环境／模型／GPU验收，不能凭相同JobID复用旧证据。

缩容在同一controller事务中将选定worker标DRAINING并停止新claim。handback明确区分已终局、当前局、未开始局；当前局依既定语义完成后先发布terminal再独立封口产物，确认sim及resident step退出后才将未开始余项发ready。只按pool账本确切JobID释放hold，不凭心跳推测退出。正常缩容不重跑已持久终局、不改seed、不消耗未开始局重试；产物错误只修artifact，不硬切动作流伪造终局。

尚未运行的PENDING job可以按确切JobID缩减；UNKNOWN提交必须先查明是否实际存在，未查明前继续计潜在占用，不能当作已释放。缩容过程中的实际存活数可暂高于新desired_jobs，但仍不得超过已批准资源上限；只有资源已确认释放才能腾出同一包络下的新容量。新增或缩减只改pool控制状态，任务160块及800局清单保持不变。

7.1 队列故障测试至少覆盖的场景

  1. 不同N的进程同时争同一chunk，只有一个 mkdir 成功；其他进程正常领下一块。
  2. claim 后 owner 前退出，控制器不得仅靠 TTL 重发；确认旧 step 终态后可恢复。
  3. worker heartbeat 停更但仍在计算，controller 不抢占；迟到合法结果仍可接受。
  4. 旧 generation 迟到，已接受新结果保持不变；旧记录进入 quarantine。
  5. controller 在 accepted 发布后崩溃，从 accepted 重建聚合得到完全相同结果。
  6. chunk 中两局 success／fail 后崩溃，只对缺失或 infra error 项按一次重试规则重发。

  13. RECOVERING期间提交结果迟到、STARTING／DRAINING／CANCEL_REQUESTED并发变化和JobID复用，均核slot_instance、incarnation、StepID与pool_revision后才能换代；无自动主备。
