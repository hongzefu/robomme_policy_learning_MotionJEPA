三、机制细节

3.1 配置键 motion.integration

定义：history yaml motion 节的可选键，决定 motion 记忆走哪条路。缺省 = 跟随顶层 integration_type（即 A、B 的现有行为）；唯一允许的显式值是在顶层 integration_type: context 下写 modulation。锚点：读取在 percep_mem.py::PerceptualMemory.__init__ 与 history_pi0.py::HistoryPi0.__init__（拟沿用 _motion_enabled 的 getattr(hc, "motion", None) 写法），校验两处、语义相同：模型侧 history_pi0.py::HistoryPi0.__init__，数据侧 framesamp_dataset.py::FrameSampDataset.__init__ 的 motion 专属守卫。

motion_integration = mcfg.get("integration", None) if motion_enabled else None
split = (integration_type == "context" and motion_integration == "modulation")
# 守卫（拟）：integration ∉ {缺省, "modulation"} → 拒；顶层非 context 却写了 integration → 拒；motion.enabled=false 时不判 motion 子键（与现有代码关闭态只判 enabled 一致）

⚠ 陷阱：(context, 2048) 与 legacy 形制 (512,64,1) 在现有白名单里早已放行，所以守卫不需要新白名单项；若误把 integration 写成第二个顶层枚举，会同时动白名单、integration_type 单值断言与 lazy_init 条件，改动面翻倍。反例：顶层 modulation 下写 integration: modulation 是同一行为的第二种写法，必须拒，否则 resolved yaml 的 sha256 不同却训练同一模型。

3.2 为什么 motion 路必须固定 1024

history_gemma.py::MemoryAttention.__call__ 硬编码 num_heads, num_kv_heads, head_dim, width = 4, 1, 256, 1024 并断言 assert mem_width == x_width == width；x 是动作专家流（宽 1024），所以送进来的 mem_seq[-1] 必须是 1024。帧路为 context 又必须是主干宽 2048。现有 memory_token_dim 是两路共用的单一输出维，表达不了「帧 2048 + motion 1024」，这正是 PerceptualMemory 要在分路时把 motion 输出维从 memory_token_dim 解绑的原因。

⚠ 陷阱：_gemma.Module.init 用 mem_mods 生成 dummy mem_seq=(1,4,c.width)，c 为动作专家配置，宽 1024，与分路一致；若分路时 lazy_init 漏传 mem_mods=[False, True]，mem_attn 参数不会初始化，前向直接报缺参。

3.3 make_attn_mask 的 na 语义

history_pi0.py::make_attn_mask(input_mask, mask_ar, mask_na=None)：cumsum(mask_ar) 构因果块，input_mask ⊗ input_mask 排除 padding；给了 mask_na 时额外屏蔽「查询或键任一为 na，且键位于首个 na 之前」的对。context 模式下记忆位于首个图像 token（na=True）之前，于是图像 token 不看记忆、记忆不看图像，文本与动作 token 看记忆。分路的前缀与纯 context 512 逐位同形，掩码自然相同（逻辑推导，由 §3.5 的结构检查与关闭态逐位核对兜底）。

⚠ 陷阱：B 的 sample_actions 写 kv_cache 用的是两参数版（前缀无记忆）；分路必须改走三参数版（带 prefix_na_mask），否则图像 token 会看到帧记忆，训练与推理掩码不一致。另一个坑：embed_prefix 内部会调用 embed_memory，若 compute_loss 为拿 motion 段再调一次，会让帧路编码器跑两遍；应设计为一次编码、两段分发（已按此设计：分路态 compute_loss / sample_actions 先调一次 embed_memory，再经 embed_prefix(obs, mem=…) 把帧段传入，见第二部分 S1-c）。

3.4 为什么 mem_order 可以保留字段但模型不读

mem_order 被 RoboMMEInputs.__call__、RepackTransform 字段映射、HistAugObservation、HistoryPi0.inputs_spec（_motion_specs 里 (B,672) int32）与 policy.py::_prepare_history 共同引用。分路下帧段进前缀、motion 段进交叉注意力，两段不在同一序列里，交错没有意义；但删字段要同时改 dataloader、推理侧与 observation 契约，还会让旧 ckpt 的 inputs_spec 变形。保留字段、模型分路分支不读，是改动最小且对旧路径零影响的做法。

⚠ 反例：motion 段的 RoPE 位置在 MemoryAttention 里是 arange(mem_len)，即 motion 段内部下标；不重排时下标顺序 = 库内时刻升序，有效位在前、补零在后并由 mem_mask 屏蔽，语义正确；若有人在分路里也套 mem_order，会拿 672 位置换去索引 160 位序列而越界。
