  • 盯盘子代理（opus，全程在线）：按用户 11-20 要求（「做评估的过程中，你这个 opus 的 agent 要持续在线来盯盯着看，但是同时你也不要把这个事情搞太复杂了，就是说你不要搞那么多什么心跳检测什么的」），两条链各派一个运行型 opus 子代理。它负责起跑 t1s-batch1（之后是 t1s-batch2），在链日志上只挂一个 Monitor（§四 的过滤管道），一直在线，直到链日志出现 EXIT_CODE=。每出现一条 T1S_ITEM 或报错行，就把原文转给主会话。不加心跳、不加定时巡检、不加额外校验，唯一的信号就是这个 Monitor。它不改代码、不改参数、不重跑、不杀会话：遇到故障，把证据交给主会话，主会话修好后，等本条链跑完，再起一条补跑链 t1s-fix<n> 跑这些 -r2 项（同样由盯盘子代理盯）。

二′ 同卡双 seed（静态配对）改动与子代理分配

为什么非改不可（只读核实）：run_shard.sh::check_local_gpu 在 LOCAL_GPU_SHARE≥2 时，要求卡上每个计算进程都是本卡占位文件 LOCAL_GPU_SLOT_FILE 里登记过的 run_shard.sh PID 的子孙，否则打印「不属于已登记分片的进程树，停止起跑」。而占位目录是 SLOT_DIR="$EVAL_ROOT/gpu-slots"，每次评估各自一份，所以另一次评估的进程必然被拒绝。端口是 PORT=18011+(SHARD_INDEX%100)*7，起跑时探测占用后顺延；两次评估同时起跑时，server 还没 bind，探测就可能放过，最后由「监听者不在本次 server 进程树」的检查判失败。改动只在评估池脚本里做，run_shard.sh 一行不动。
